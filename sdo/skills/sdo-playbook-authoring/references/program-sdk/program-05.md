type RepairData struct {
	Target          StoreTarget
	Scope           DataScope
	Statement       string
	MemberPredicate *MemberPredicate
	CopyFrom        *DataScope
	ExpectMin       int
	ExpectMax       int
	Backup          string
	Reason          string
}
    RepairData runs one write on a scope. Its effect is data-write. It sets
    exactly one of:
      - Statement: a redis single-key write per matched key ("SREM member"),
        a mongodb update document or pipeline, a postgres or mysql SET clause,
        or "delete" (the only memcached statement);
      - MemberPredicate (redis): remove the members it selects from every set,
        sorted set or list the scope matches, for example the members that are
        not digits or whose "post:{member}" key is missing;
      - CopyFrom: copy every item of the CopyFrom scope that Scope's namespace
        lacks into it (a renamed collection, table or key pattern back under its
        name; redis merges sets and sorted sets member by member). Scope names
        the target namespace whole; CopyFrom is left as it is.

    The controller counts the matching items first (the CopyFrom items for a
    copy) and refuses unless the count is within [ExpectMin, ExpectMax], writes
    (atomically with the count on redis, postgres and mysql), then counts Scope
    again and reads the store's facts. Backup optionally names a StoreBackup of
    this incident; the controller records it and whether it covers Scope.

type RestartRollout struct {
	Ref    sdk.ObjectRef
	Reason string
}
    RestartRollout restarts a workload's Pods like kubectl rollout restart. It
    stamps the Pod template's kubectl.kubernetes.io/restartedAt annotation, and
    the workload's own update strategy replaces the Pods. Pods the controller
    will not replace (an OnDelete strategy, or an OrderedReady StatefulSet
    waiting on an unready Pod) are deleted so they restart too; the receipt
    names each deleted Pod and why. Ref must be one named apps/v1 Deployment,
    StatefulSet or DaemonSet.

type RestoreBackup struct {
	Target StoreTarget
	Backup string
	Reason string
}
    RestoreBackup puts an incident's StoreBackup back. Its effect is data-write:
    redis keys are restored with REPLACE, mongodb documents upserted by _id,
    postgres rows replaced by primary key in one transaction, mysql rows with
    REPLACE in one transaction, memcached items set again with their flags
    and expiry. Items created since the backup stay, and writes made since the
    backup to the restored items are lost: name them in the outcome. A fresh
    StoreBackup of the same scope first is recorded as holding what the restore
    overwrote.

func (a RestoreBackup) Validate() error

type RestoreStoreItem struct {
	Target      StoreTarget
	Change      storestate.Change
	EndSessions bool
	Reason      string
}
    RestoreStoreItem puts a store-state item back to its baseline.
    Its effect is store-setting. Change names the item, normally one entry of
    storestate.Changes(view) for the Target Pod; the controller restores the
    value of its own promoted healthy baseline, not the one in Change. It runs
    the engine's fixed inverse (storestate.RestoreCommands): CONFIG SET, ACL
    SETUSER, REPLICAOF NO ONE or CLIENT UNPAUSE on redis; collMod, fsyncUnlock,
    dropIndexes/createIndexes, setParameter or updateUser on mongodb;
    ALTER SYSTEM/DATABASE/ROLE or pg_promote on postgres. A validator or index
    text comes from the restore text the controller captured with the baseline.
    A password is restored only from the store container's own environment.
    The executor reads the item first and records its prior value, does
    nothing when it already has the baseline value, and reads the facts again
    to verify it. EndSessions also ends the sessions a restored per-database
    or per-role postgres setting applies to, so clients reconnect with it.
    storestate.Restorable says beforehand whether an item has an inverse.

func (a RestoreStoreItem) Validate() error

type RetireOldRevision struct {
	Ref sdk.ObjectRef
}
    RetireOldRevision scales one old-revision ReplicaSet of a Deployment to
    zero. It releases a rollout whose replacement Pod cannot be placed or
    created while the old revision's Pod holds its place (hard anti-affinity,
    a host port, node capacity or namespace quota). The Deployment controller
    never scales a retired revision back up. It is refused like any ReplicaSet
    scale for a current revision or a ReplicaSet without an observed controlling
    Deployment.

    proof of admission or application recovery; independent verification remains
    required. Webhook repairs automatically include retries for affected sets.
