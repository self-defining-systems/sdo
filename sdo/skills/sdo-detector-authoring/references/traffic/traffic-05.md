type SLO struct {
	Window         int      `json:"window,omitempty"`
	MinSamples     int      `json:"minSamples,omitempty"`
	MaxAge         Duration `json:"maxAge,omitempty"`
	MaxErrorRate   float64  `json:"maxErrorRate,omitempty"`
	MaxTimeoutRate float64  `json:"maxTimeoutRate,omitempty"`
	// MinTimeouts is the minimum timeout count before timeouts contribute to
	// either rate violation. Defaults to two so one scheduling pause is noise.
	// The effective floor is capped at Window so a total timeout outage fires.
	// Set one explicitly for strict timeout objectives.
	MinTimeouts       int      `json:"minTimeouts,omitempty"`
	LatencyPercentile int      `json:"latencyPercentile,omitempty"`
	MaxLatency        Duration `json:"maxLatency,omitempty"`
}
    SLO bounds a scenario's recent behaviour. Zero fields inherit the workload's
    SLO, and then the package defaults. The default latency bound applies to
    the median; one timeout remains evidence but does not contribute to rate
    violations until MinTimeouts is reached.

func Evaluate(scenarioID string, slo SLO, samples []Sample, now time.Time) SLOVerdict
    Evaluate judges samples (oldest first) of one scenario at now. Invalid
    samples and samples older than the SLO's maxAge are ignored, only the
    latest window samples count, and fewer than minSamples leaves the scenario
    unevaluated, which is healthy.

func Judge(window Window) []SLOVerdict
    Judge evaluates every qualified scenario of window at its ObservedAt,
    except those the workload declares KnownBroken: they never gate health.

type Sample struct {
	At        time.Time     `json:"at"`
	Latency   time.Duration `json:"latency"`
	Iteration uint64        `json:"iteration"`
	// Status is the last HTTP status received, or 0 when none arrived or
	// the last answer was an exit status.
	Status int `json:"status,omitempty"`
	// Exit is the exit status of the last EXEC, when the last answer was
	// one.
	Exit    *int    `json:"exit,omitempty"`
	Outcome Outcome `json:"outcome"`
	// Step names the step that failed; Request is its method and URL path
	// with query, so the failure can be reproduced by hand.
	Step    string `json:"step,omitempty"`
	Request string `json:"request,omitempty"`
	// Error explains a failed sample: the transport error, the check's
	// reason, or a bounded excerpt of the unexpected response body.
	Error string `json:"error,omitempty"`
	// Observed is what the other side answered, apart from the probe's own
	// Error: a bounded, redacted excerpt of the server's response body, or the
	// transport error cause without the client's method and URL prefix.
	Observed string `json:"observed,omitempty"`
	// DialFailed marks a failure that happened while establishing the
	// connection (DNS or TCP dial), rather than while sending the request,
	// reading the response, or checking it. A NetworkPolicy or a stopped
	// listener that refuses new connections shows up here, distinctly from
	// an application-level error or a slow response, whether the dial
	// failed outright (Outcome error) or hung until the dial timeout
	// (Outcome timeout).
	DialFailed bool `json:"dialFailed,omitempty"`
	// IdentityWait is set on an invalid sample whose probe user was still
	// being provisioned: how long one provisioning run may take. Such a sample
	// is an environment wait, not a finding about the application.
	IdentityWait time.Duration `json:"identityWait,omitempty"`
	Requests     int           `json:"requests"`
	// ExistingRecords says what the scenario's ReadsExistingRecords step saw
	// on an iteration that passed: exercised, own-only or empty. It is an
	// operability note, never a failure: a fresh install has no user data.
	ExistingRecords string `json:"existingRecords,omitempty"`
	CleanupError    string `json:"cleanupError,omitempty"`
}
    Sample is the observed result of one scenario iteration.

type Scenario struct {
	ID          string
	Description string
	Target      Target
	DependsOn   []string
	SideEffect  SideEffect
	Marker      string
	Setup       []Step
	Steps       []Step
	Cleanup     []Step
	Detects     []FaultClass
	// Users are the probe users the scenario signs in as; see ProbeUser.
	Users []ProbeUser
}
    Scenario is one user journey. DependsOn names the Services on its request
    path, as described in .sdo/arch.md, so a failing scenario localizes the
    fault. Writes must use dedicated synthetic data whose Marker appears in
    every write request.

    Setup steps create the scenario's own test data (a test identity,
    a fixture a later read must find) so the scenario never depends on data set
    up by hand. The engine runs them at the start of the first iterations until
    each has succeeded once; a retry resumes at the first step that has not
    succeeded, with the State the earlier ones saved, so a step that succeeded
    (one that created a credential, say) is not repeated when a later one fails.
    Data lost afterwards then fails the Steps instead of being written again,
    also in the controller's verify bursts, which share the continuous probe's
    setup. Setup requests may write in any scenario and must carry the Marker;
    make them idempotent (OrExisting) because a restarted prober runs them
    again. Values they save are visible to every iteration.

func (s Scenario) Describe() Descriptor
    Describe returns the scenario's descriptor with its effective fault classes.

func (s Scenario) ExistingRecordsSteps() []ExistingRecordsStep
    ExistingRecordsSteps reports the scenario's steps marked with
    ReadsExistingRecords. To find the keys a marked step templates, it builds
    the step's request with every key a step saves set to a distinct sentinel
    and looks for the sentinels in the request, so it holds for any parameter
    generator.

func (s Scenario) FaultClasses() []FaultClass
    FaultClasses returns the required classes followed by the declared ones.

func (s Scenario) StatusOnly() bool
    StatusOnly reports whether every step (setup excluded) is a declarative
    HTTPEndpoint that checks nothing but the status, so the scenario cannot tell
    a wrong or empty answer from a correct one.

func (s Scenario) Validate() error
    Validate reports the first problem that makes the scenario unsafe or
    ambiguous. Rules that depend on built requests (read scenarios send only
    GET/HEAD; writes carry the marker) are enforced by the engine per request;
    a declarative HTTPEndpoint step of a read scenario is also checked here.

type SideEffect string
    SideEffect classifies what a scenario does to application state.

const (
	// SideEffectRead scenarios send only GET and HEAD requests.
	SideEffectRead SideEffect = "read"
	// SideEffectIdempotentWrite scenarios write the same dedicated synthetic
	// data every time, so repeating them changes nothing further.
	SideEffectIdempotentWrite SideEffect = "idempotent-write"
	// SideEffectWriteWithCleanup scenarios create synthetic data and remove
	// it again with their Cleanup steps.
	SideEffectWriteWithCleanup SideEffect = "write-with-cleanup"
)
type Source interface {
	TrafficWindow(workload string) (Window, bool)
}
    Source is implemented by detection contexts that carry synthetic-traffic
    observations. The controller runtime's snapshots implement it.

type State map[string]string
    State carries values between the steps of one iteration, for example an
    ID a create step saved for the read and cleanup steps that follow. Every
    iteration starts with an empty State.

type Step struct {
	Name     string
	Endpoint Endpoint
	Target   *Target
}
    Step is one named request of a scenario. Target, when set, overrides the
    scenario's target for this step, so one journey can, for example, register a
    key over HTTP and then use it over SSH. Its Service must be the scenario's
    target or one of its DependsOn.

type Target struct {
	Service string `json:"service"`
	Port    int    `json:"port"`
	Scheme  string `json:"scheme,omitempty"`
	User    string `json:"user,omitempty"`
}
    Target is the Service, in the application namespace, a scenario calls.
    Scheme is "http" (the default), "https" or "ssh"; User is the SSH login name
    and is set exactly when Scheme is "ssh".
