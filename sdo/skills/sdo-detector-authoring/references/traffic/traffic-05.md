type Scenario struct {
	ID          string
	Description string
	Target      Target
	DependsOn   []string
	SideEffect  SideEffect
	Marker      string
	Setup       []Step
	Steps       []Step
	Cleanup     []Step
	Detects     []FaultClass
	// Users are the probe users the scenario signs in as; see ProbeUser.
	Users []ProbeUser
}
    Scenario is one user journey. DependsOn names the Services on its request
    path, as described in .sdo/arch.md, so a failing scenario localizes the
    fault. Writes must use dedicated synthetic data whose Marker appears in
    every write request.

    Setup steps create the scenario's own test data (a test identity,
    a fixture a later read must find) so the scenario never depends on data set
    up by hand. The engine runs them at the start of the first iterations until
    each has succeeded once; a retry resumes at the first step that has not
    succeeded, with the State the earlier ones saved, so a step that succeeded
    (one that created a credential, say) is not repeated when a later one fails.
    Data lost afterwards then fails the Steps instead of being written again,
    also in the controller's verify bursts, which share the continuous probe's
    setup. Setup requests may write in any scenario and must carry the Marker;
    make them idempotent (OrExisting) because a restarted prober runs them
    again. Values they save are visible to every iteration.

func (s Scenario) Describe() Descriptor
    Describe returns the scenario's descriptor with its effective fault classes.

    FaultClasses returns the required classes followed by the declared ones.

func (s Scenario) StatusOnly() bool
    StatusOnly reports whether every step (setup excluded) is a declarative
    HTTPEndpoint that checks nothing but the status, so the scenario cannot tell
    a wrong or empty answer from a correct one.

func (s Scenario) Validate() error
    Validate reports the first problem that makes the scenario unsafe or
    ambiguous. Rules that depend on built requests (read scenarios send only
    GET/HEAD; writes carry the marker) are enforced by the engine per request;
    a declarative HTTPEndpoint step of a read scenario is also checked here.

type SideEffect string
    SideEffect classifies what a scenario does to application state.

const (
	// SideEffectRead scenarios send only GET and HEAD requests.
	SideEffectRead SideEffect = "read"
	// SideEffectIdempotentWrite scenarios write the same dedicated synthetic
	// data every time, so repeating them changes nothing further.
	SideEffectIdempotentWrite SideEffect = "idempotent-write"
	// SideEffectWriteWithCleanup scenarios create synthetic data and remove

type State map[string]string
    State carries values between the steps of one iteration, for example an
    ID a create step saved for the read and cleanup steps that follow. Every
    iteration starts with an empty State.

type Step struct {
	Name     string
	Endpoint Endpoint
	Target   *Target
}
    Step is one named request of a scenario. Target, when set, overrides the
    scenario's target for this step, so one journey can, for example, register a
    key over HTTP and then use it over SSH. Its Service must be the scenario's
    target or one of its DependsOn.

type Target struct {
	Service string `json:"service"`
	Port    int    `json:"port"`
	Scheme  string `json:"scheme,omitempty"`
	User    string `json:"user,omitempty"`
}
    Target is the Service, in the application namespace, a scenario calls.
    Scheme is "http" (the default), "https" or "ssh"; User is the SSH login name
    and is set exactly when Scheme is "ssh".

func (w Window) IdentityWait() time.Duration
    IdentityWait is the longest provisioning run any scenario is still waiting
    for, zero when none waits on a probe user.

func (w Window) LinkSetting() LinkSetting
    LinkSetting returns the setting of the window's link-probe workload.

func (w Window) Ready() bool
    Ready reports whether the window holds what its own detectors need to judge
    it: every observed scenario has the usable samples its SLO requires (failed
    samples count, so an outage is judged rather than waited out), and every
    link has a sample. The traffic detector's ConfirmationReason is built on the
    same predicate, so a ready window can differ from a confirmed one only by
    scenarios that have not yet succeeded.

func (w Window) SLO() SLO
    SLO returns the workload's effective SLO, defaults included.

func (w Window) WarmupHorizon() time.Duration
    WarmupHorizon is how long a freshly started prober needs, at the workload's
    rate, to give every scenario its SLO's minimum samples.
