# Store data: backup, cache invalidation, repair, restore

Use these typed actions (menu or plan) for records inside a data store. Each needs a `StoreTarget`: the application-map component, its `data.engine` (redis, mongodb, postgres), and the store Pod and container. SDO refuses a target the accepted map does not ground. A `DataScope` selects records: redis database number and key glob; mongodb database, collection and JSON filter; postgres database, table and WHERE body. `Limit` bounds the items (default 10000).

Work in this order:

1. **Fix the authoritative source first.** A cache refills from its source, so flushing it over damaged source records brings the damage back. Find and repair the damage in the store the map marks `role: authoritative` before you touch a `derived` one.
2. **Back up when you may want the records back.** `StoreBackup{ID, Target, Scope}` copies the scope to the controller's backup storage and records the item count, size, SHA-256 and store facts. It changes nothing. Back up the whole collection or table, or exactly the scope you will repair.
3. **Repair with a count.** First count the scope with a read and decide how many items the repair should touch. Then run `RepairData{Target, Scope, Statement, ExpectMin, ExpectMax}`, with `Backup` naming a `StoreBackup` of this incident if you took one. SDO counts again and refuses outside the bounds. Then it writes and counts again, and the receipt reports before, affected and after, the backup you named and whether it covers the scope. The statement is one redis single-key write applied to each matched key (`SREM <member>`, `HDEL <field>`, `DEL`), a mongodb update document or pipeline (`{"$rename": {"addr": "address"}}`), a postgres `SET ...` clause, or `delete`.
4. **Invalidate the copy last.** `InvalidateDerived{Target, Scope}` drops redis cache entries. The receipt's `source_state` records whether the map marks the component `derived` and how each `derived_from` source read; a source that fails its store-state checks means the cache will refill with the damage, so go back to step 1.
5. **Restore only deliberately.** `RestoreBackup{Target, Backup}` puts a backup's items back: redis keys with REPLACE, mongodb documents upserted by `_id`, postgres rows by primary key. It never deletes items created since the backup. A fresh `StoreBackup` of the same scope first keeps what the restore overwrites.

**Name lost writes.** A restore discards every write the application made to the restored items after the backup. A repair can conflict with writes that land between its count and its write. In your report, give the backup time, the restore or repair time, and the keys, documents or rows that may have changed in between.

SDO records, but never refuses, the data effect of every action that reaches a `holds_data` store: `sdo verify` lists them in `data_effects[]` and the outcome keeps them as notes, saying for each write whether a backup of this incident held what it could change. They do not change the outcome. The automatic stage runs these actions too.
