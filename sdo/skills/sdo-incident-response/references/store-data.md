# Store data: backup, cache invalidation, repair, restore, store settings

Use these typed actions (menu or plan) for records inside a data store. Each needs a `StoreTarget`: the application-map component, its `data.engine` (redis, mongodb, postgres, mysql, memcached), and the store Pod and container. SDO refuses a target the accepted map does not ground. A `DataScope` selects records: redis database number and key glob; mongodb database, collection and JSON filter; postgres or mysql database, table and WHERE body; memcached key glob (keys are listed with `lru_crawler metadump`). `Limit` bounds the items (default 10000).

Work in this order:

1. **Fix the authoritative source first.** A cache refills from its source, so flushing it over damaged source records brings the damage back. Find and repair the damage in the store the map marks `role: authoritative` before you touch a `derived` one.
2. **Back up when you may want the records back.** `StoreBackup{ID, Target, Scope}` copies the scope to the controller's backup storage and records the item count, size, SHA-256 and store facts. It changes nothing. Back up the whole collection or table, or exactly the scope you will repair.
3. **Repair with a count.** First count the scope with a read and decide how many items the repair should touch. Then run `RepairData{Target, Scope, Statement, ExpectMin, ExpectMax}`, with `Backup` naming a `StoreBackup` of this incident if you took one. SDO counts again and refuses outside the bounds. Then it writes and counts again, and the receipt reports before, affected and after, the backup you named and whether it covers the scope. The statement is one redis single-key write applied to each matched key (`SREM <member>`, `HDEL <field>`, `DEL`), a mongodb update document or pipeline (`{"$rename": {"addr": "address"}}`), a postgres or mysql `SET ...` clause, or `delete` (the only memcached statement). In place of `Statement`, `MemberPredicate` (redis) removes the members it selects from every matched set, sorted set or list: `NotDigits`, `MissingKey: "post:{member}"` (a dangling reference), `In` or `NotIn` lists; and `CopyFrom: &DataScope{...}` copies every item of a renamed namespace that `Scope` lacks back into it (a collection or table copied by key, redis keys `<prefix>*<suffix>` mapped to `Scope`'s glob with sets and sorted sets merged member by member); the bounds then count the `CopyFrom` items, and the source stays until you delete it with a second repair.
4. **Invalidate the copy last.** `InvalidateDerived{Target, Scope}` drops cache entries: redis keys of the glob; memcached `flush_all` for the whole-cache glob `*`, else the keys of the glob. The receipt's `source_state` records whether the map marks the component `derived` and how each `derived_from` source read; a source that fails its store-state checks means the cache will refill with the damage, so go back to step 1.
5. **Restore only deliberately.** `RestoreBackup{Target, Backup}` puts a backup's items back: redis keys with REPLACE, mongodb documents upserted by `_id`, postgres rows by primary key, mysql rows with REPLACE, memcached items set again with their flags and expiry. It never deletes items created since the backup. A fresh `StoreBackup` of the same scope first keeps what the restore overwrites.

## Store settings, credentials and connections

A store-state finding names one changed item (a setting, write block, role, principal, validator, index or lock). `RestoreStoreItem{Target, Change}` puts it back to the controller's healthy baseline with the engine's own command: redis `CONFIG SET`, `ACL SETUSER` (passwords untouched), `REPLICAOF NO ONE`, `CLIENT UNPAUSE`; mongodb `fsyncUnlock` until unlocked, `collMod` (a changed validator is put back from text captured with the baseline), `dropIndexes`/`createIndexes`, `setParameter`, `updateUser`; postgres `ALTER SYSTEM`/`ALTER DATABASE`/`ALTER ROLE` settings and role flags, `pg_promote`, dropping a constraint, trigger or index added since the baseline. A write block is restored through the setting it follows from. `EndSessions: true` also ends the postgres sessions a restored per-database or per-role setting applies to, so pools reconnect with it. The receipt's `store_restore` records the baseline, prior and verified values; an item already at its baseline is left alone. A password is restored only from the store container's own environment; an item without an exact inverse is refused with the reason.

`CheckStoreCredential{Target, Client, Container}` tells a password changed on the server from a wrong client Secret: SDO runs one short-lived Pod with the store's image and the client container's env references (never reading them) and authenticates once. `store_credential.result` is `ok`, `denied` or `unreachable`; `denied` while the client's Secret is unchanged means the server's credential changed. Name the client's variables in `Credential` when discovery would pick the wrong ones.

`storestate.Changes(view)[i].Holders`, and the evidence of a connection-cap or `max-clients` finding, group a store's connections by peer and state (`idle`, `active`, `idle-in-transaction`, `blocked`; `connected` when the store refused its session list and the TCP table was read) with each peer's Pod and workload; `local` is a process inside the store Pod.

A `store-state.lock-waiters` finding (postgres, mysql) names a session that holds a lock other sessions have waited on for over 30 s, on a table where the healthy history shows no such wait: the holder's session id, peer (with its Pod and workload), state, lock mode, the locked table, the waiter count, the longest wait and the holder's transaction age (`storestate.Facts.LockWaits`). Ending the holder with the store's own command (postgres `pg_terminate_backend`, mysql `KILL`) releases the lock and rolls back its open transaction; when the holder is an application Pod, find out why its work does not finish too. A `locked` refusal means SDO's own read gave up waiting on such a lock.

**Name lost writes.** A restore discards every write the application made to the restored items after the backup. A repair can conflict with writes that land between its count and its write. In your report, give the backup time, the restore or repair time, and the keys, documents or rows that may have changed in between.

SDO records, but never refuses, the data effect of every action that reaches a `holds_data` store: `sdo verify` lists them in `data_effects[]` and the outcome keeps them as notes, saying for each write whether a backup of this incident held what it could change. They do not change the outcome. The automatic stage runs these actions too.
