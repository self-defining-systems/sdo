# SDO experiment evidence reference

Use this reference to correlate durable production evidence with SREGym artifacts. Field sets may grow; inspect the run's schema/version and repository models before assuming optional fields.

## Evidence hierarchy

For production-lifecycle claims, use this order:

1. strict production receipt;
2. controller-owned outcomes and durable runtime state;
3. broker incident ledger and attributable Git commits;
4. lifecycle provenance and validated operational memory;
5. controller, responder, validator, and harness logs;
6. agent-specific trajectories.

A benchmark result can establish the harness verdict. It cannot by itself establish memory ownership, independent verification, reflection, rollout, or cleanup.

## Lifecycle provenance

Path: `.sdo/lifecycle-provenance.yaml`

Expected sections:

- `deployer`: session ID, source commit, topology fingerprint, resource inventory, and architecture summary. The model returns only the commit, fingerprint, and summary; the controller attaches the resource inventory deterministically from tracked manifests, so the inventory is a controller fact rather than model output.
- `active_topology` (when supplied by the deployment adapter): sorted kind/name references for the deployed source variant and required non-optional ConfigMap dependencies.
- `health_judge`: the accepted final detector artifact.
- `health_judge_rounds`: ordered structured attempts with distinct session IDs, round numbers, objective digest, covered resources, source, and tests.
- `validation` (when the validator exposes an immutable identity): the diagnostics-tree digest, immutable validator identity, and `sdo.lifecycle-validation/v1` attestation schema. An exact match permits validation reuse without recompilation; a missing or mismatched field requires fresh isolated validation.

Correlate the deployer source commit with Git and `arch.md`. Correlate the objective digest with the exact text in `goal.md`. When `active_topology` is present, verify that `covered_resources` contains no inactive source variants. A reused lifecycle is credible only when current source topology, active topology, and detector validation still match.

## Outcome records

Phase-1 program memory stores responder-owned Go `diagnose.go`, optional `mitigate.go`, and tests beside judgement guidance in `.sdo/playbooks/<fault-class>/`. Shared helpers and their `metadata.yaml` incident provenance are under `.sdo/lib/<package>/`; labeled replay cases are under `.sdo/corpus/<case>/` with `open.json`, `fixed.json`, `healthy.json`, `recordings.json`, and `labels.json`. The Go memory edge materializes these from typed proposals. The isolated validator and `draft-test` compile and replay them; a program's presence alone does not show runtime use or a mitigation. Correlate any later program-use claim with controller outcomes and accepted commits.

Reflection may instead return `learning_decision=sdk_gap` with typed `sdk_gaps` entries (`fault_class`, missing `primitive`, `reason`, and `scratch_script`). These are in the durable native broker ledger's `reflection_decision`, joined to the immutable outcome by incident ID and `outcome_commit`; they record a proven check the current SDK could not express, not an accepted program or repair. An `updated` decision may also carry gaps for other faults. For an accepted program, inspect the reflection commit's playbook sources and corpus labels, then the broker validation evidence; the proposal or draft-test result alone does not prove acceptance.

The logical outcome schema is `OutcomeRecord` in `sdo/contracts/proto/sdodev/contracts/v1alpha1/outcome.proto`. The active Go memory adapter stores one versioned JSON document per incident at `.sdo/outcomes/<sha256(incident_id)>.json`; its logical `Reader` lists and gets records by incident ID, while only the broker has `Writer` capability. Reflection tasks carry the accepted current and prior outcomes as typed protobuf records. The adapter can import a retired `.sdo/outcomes.jsonl` stream and removes that stream only after every record is accepted. Correlate incident IDs and outcome commit hashes with the native broker ledger and benchmark `production-receipt/v2`. Important fields include:

- `incident_id`, `source_commit`, `deployed_commit`;
- detector history, findings, and final health-detector state;
- surfaced, inspected, confirmed, rejected, and applied playbooks;
- confirmed root causes. Newer results give each cause `evidence` (live items only: `detector-finding`, `synthetic-traffic`, `state-change`, or `live-observation`, each with `source` and `observation`), `explained_detectors` (detectors that must clear after the fix), and `static_context` (scripts, manifests, ConfigMap bodies, or notes that motivated the hypothesis but prove nothing). Older records have these empty;
- `diagnosis_verification` (absent in older records): per root cause, SDO's deterministic `verdict` (`confirmed`: every explained detector fired at dispatch and cleared after the fix, and no cited evidence is contradicted; `contradicted`: some cited detector, scenario, or state change was never observed by the controller, the signature of a red-herring diagnosis; `unverified`: no contradiction but the detectors did not all flip; `unattributed` (absent in records before repair attribution): the detectors flipped, but the responder's own repair does not back the cause; `no-evidence`: a legacy cause), the per-item `evidence` checks (`verified` true, false, or null for unverifiable live observations, and `reason` (absent before rc2) when a reference existed but is not evidence), the `detectors` flips, and `repair` (absent in records before repair attribution): `attributed`, the backing `actions` (IDs of successful repair actions that started by the closure's `health_cleared_at` and touched the cause's resources), `repaired_resources` (`Kind/name`), `externally_reverted` (dispatch-diff objects gone from `final_state_changes` that no responder repair touched), and a `reason`. A cause is attributed when such an action touched one of its resources (or a `state-change` object it cites) that was in the dispatch diff; a cause whose touched resources are not in the dispatch diff (a runtime fault, a late composite component, or a restarted workload) is attributed only when `externally_reverted` is empty. Each cause of a composite is attributed to its own repair, so with one repaired component only that cause is `confirmed`. `unattributed` means someone else most likely fixed the fault inside the verification window while the responder claimed a wrong cause; A `state-change` evidence check is verified against the union of `request.state_changes` and `final_state_changes` (see the broker ledger below), so a cause citing a composite's late-landing fault is not `contradicted` merely because it missed the dispatch-time snapshot; when the closure carries `observed_state_changes` (rc2), a citation outside the dispatch diff must instead appear there with a `first_observed_at` earlier than the start of the responder's first repair action on that object, otherwise it is `verified: false` with a `reason` naming that action (the responder cited its own edit, such as a restart's `restartedAt`), and a late fault the responder reverted exactly still verifies from that record;
- `classification`: `success`, `partial` (health cleared only after the verification window), `external_recovery` (health cleared in time, but every cause is unattributed, so the recovery is not credited to SDO; `verified_at` is still set), `false_positive`, `false_negative`, `failed`, `cancelled`, or `cleared_without_action` (health verified clear, but the responder made no successful change, whether it reported `completed` or `cancelled`; older records classed the `completed` case as `cancelled`; it is not a mitigation). The broker never reflects on `partial`, `external_recovery` or `cleared_without_action`, and the controller never surfaces them, or a `contradicted`/`unattributed` cause of a `success`, as prior-outcome evidence;
- repair and memory commits, plus structured live repair-action receipts; newer receipts carry `resources`, the objects each action mutated (older ones only a free-form `target`, parsed as `[namespace/]Kind/name` when possible);
- responder backend/model and transport-reported usage (`llm_calls`, `input_tokens`, `cache_read_input_tokens`, `cache_write_input_tokens`, `cache_write_1h_input_tokens`, `uncached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `model_requests`, and `total_cost_usd` when the provider reports it). `cached_input_tokens` is the deprecated alias of cache reads; a record without `cache_read_input_tokens` predates agentshim 0.7, and on Claude its `cached_input_tokens` also counted cache writes (subtract `cache_write_input_tokens` to get reads);
- detected, dispatched, mitigated, verified, and completed timestamps.

The controller runtime ConfigMap can also contain `detector_review_required`, `detector_review_required_at`, and `detector_review_reason`. These fields mean a responder completed but independent health findings did not clear within the bounded verification window; do not interpret that state as a verified incident closure.

Useful queries for the active per-incident outcome documents:

```bash
jq -s 'map({incident_id, classification, repair_commit, memory_commit, diagnosis_verification})' .sdo/outcomes/*.json
jq -s 'group_by(.classification) | map({classification: .[0].classification, count: length})' .sdo/outcomes/*.json
```

The filename is a hash, not an incident ID. For a historical checkout containing JSONL, inspect its accepted Git revision and import state before combining counts.

## Broker incident ledger

For active Go runs, inspect the configured runtime `LedgerRoot` and the Go broker workspace root. The broker stages trusted source deployment evidence before publishing source, then reconciles that evidence to the attributed accepted commit after a crash. The evidence binds the candidate Git tree, strategy, immutable image digests, resource IDs, and observed ready revision; agent claims and annotations alone are not authoritative.

Ledger fields can include proposal processing state; optional proposal commit; mandatory outcome, reflection, and validator-evidence commits; responder session ID; accepted detector paths; closure and acknowledgement state; network-policy canaries; topology fingerprints; and controller-update rollout records. `reflection_attempts` counts reflection turns, including turns whose backend failed; `reflection_backend_error` (absent in older ledgers) is the last such failure, and once the attempts are spent the broker records `no_change` with that error as the reason instead of failing the closure; `reflection_fresh_retry_attempts` (default 0 in older ledgers) counts the subset that retried a validator-rejected proposal in a fresh session instead of resuming the responder session. `reflection_session_mode` (null in older ledgers and when no LLM reflection ran) records how the first attempt ran: `resume` (the default: the responder session when its ID is valid) or `fresh` (a new session given a bounded incident brief of the closure findings and observed state changes, the responder's structured result, its shell commands from `responder-turns.jsonl`, and relevant memory excerpts; under about 8K tokens). It is fixed when the first LLM attempt starts, so a restarted broker keeps it. The rejected proposal's diff is kept beside the ledger as `<sha256(incident_id)>.reflection-rejected.diff`. `reflection_skipped_reason` (null in older ledgers) is set when the broker recorded a deterministic no-op reflection without an LLM turn: a repeated exact-match success where the warm rule held (a prior verified outcome matched by `exact-fingerprint`, or by `learned-detector-origin` when an incident detector learned from that outcome fired on the same resource and surfaced a playbook listed in the `possiblePlaybooks` of a registered responder-owned incident detector, fired or not), the responder applied that playbook, every repair action and verification passed, the controller verified health, and that detector was not firing in its latest post-response evaluation (no post-response evaluation is accepted). The reason names the prior incident(s), each playbook with its detector, whether the detector had fired at dispatch, how the playbook surfaced (`active-finding`, `surfaced`, `prior-outcome-applied`, `detector-learned-from-exact-prior`), and each detector's post-response state (`clear after the response` or `not evaluated after the response`). Such a ledger has `reflection_attempts=0`, empty `reflection_usage`, `reflection_learning_decision=no_change` with the same text as `reflection_no_change_reason`, an empty attributable reflection commit, and no accepted detector paths or controller rollout. The closure's `request.state_changes` (absent in older ledgers or without a healthy baseline) is the controller's configuration diff against its last healthy baseline when the incident opened: `baseline_at`, `observed_at`, `changes` (`kind`, `name`, `change` of `added`/`removed`/`modified`, and field-level `before`/`after`, where ConfigMap and Secret data appear only as `sha256:` digests), `omitted`, and `unobserved_kinds`; objects that existed unchanged at the baseline, such as SREGym's `failure-admin-*` decoys, never appear. The closure's `final_state_changes` (absent in ledgers before the verification-time state diff, and without a healthy baseline) is the same shape of diff, recomputed at verification time instead of dispatch time: a composite fault's later component can land a few seconds after dispatch while the incident is still open (K2's readiness-probe fault about 6s after its selector fault), so it can appear here without appearing in `request.state_changes`. `verify_diagnosis` checks `state-change` evidence against the union of both, so a diagnosis citing only the late component is `confirmed`/`unverified` rather than `contradicted`; a change absent from both is still `contradicted`. The closure's `observed_state_changes` (absent before rc2, and without a healthy baseline) lists every object the controller saw differ from the baseline while the incident was open (`kind`, `name`, `first_observed_at`): the dispatch diff, each evaluation's incident-view diff, and the closing view; it is what dates a `state-change` citation against the responder's repair. The closure's `health_cleared_at` (absent in ledgers before repair attribution, and when a gate detector had no clear streak on record) is when the closure gate's detectors began their final streak of clear evaluations; only a repair action that started by then can back a root cause. The closure's `cleaned_helpers` (absent in older ledgers) lists the responder helper pods and Jobs (`sdo.dev/responder-helper=true`) the controller deleted when the responder completed. The closure's `incident_detector_states` (absent in older ledgers) holds the latest post-response evaluation of each non-health detector that raised a finding; it is learning evidence, not a closure gate. The closure's `detector_review_required_at` and `detector_review_reason` (absent in older ledgers and when health cleared in time) mark health that cleared only after the controller's verification window expired; the broker then treats health as unverified for the responder (classification `partial`, no `verified_at`, no reflection), and the receipt's `detector_review_required_at` makes strict validation reject it. Under `recorded-actions`, a missing proposal commit is valid only when the result and outcome contain a successful structured repair action. Require incident IDs and commit hashes to agree with the receipt and outcome.

## Strict production receipt

Path in an SREGym problem run: `agent/sdo_production_receipt_strict.json`.

The active schema is `sdo.production-receipt/v2`, assembled by the benchmark adapter from native Go `incident-evidence` and correlated Kubernetes observations. The receipt embeds the raw `native_ledger`, the controller image and Pod UID, responder Job UID/success evidence, proposal/outcome/reflection commit hashes, outcome classification, and a resolution derived from that classification. Native reflection usage is in `native_ledger.reflection_decision.usage` and copied to top-level `reflection_usage`; the latter is the analysis fallback when rollouts are unavailable. `broker_mode=native` and `worker_mount_mode=proposal-only` are required. Validate it with `benchmarks.sregym.protocol.native_receipt.validate_native_production_receipt` before interpreting fields.

A valid v2 receipt binds one incident ID across request, result, outcome, closure receipt, responder Job, and acknowledged broker ledger. It requires independently clear detector states, a verified outcome diagnosis and repair, reflection when required, and a matching controller detector rollout. A benchmark verdict alone proves none of these. `resolution` distinguishes `sdo_mitigated`, `external_recovery`, and `cleared_without_sdo_action`; count only the first as SDO mitigation. Older `sdo.production-receipt/v1` documents are archived evidence and must be interpreted using their declared schema, never silently normalized into v2.

Controller runtime artifacts are exported under `agent/sdo_runtime/`. Durable usage and telemetry streams remain cumulative across incidents, so scope by incident ID and timestamps. Session transcripts live under `sdo_runtime/sessions/<incident-hash>/{codex,claude}/` and are retained for seven days after durable acknowledgment, with daily pruning. A resumed reflection may share the responder session; use its turn timing and session ID to attribute cost, not the whole transcript. Persistent benchmark stages may publish a deferred receipt after the following stage drains the previous incident; require the receipt's incident ID and native ledger to agree before joining it to an oracle result.

## SREGym result tree

Typical paths:

```text
third_party/sregym/logs/<run-or-pipeline>/
├── experiment_config.toml or pipeline_config.toml
├── run_manifest.json                       # launch provenance (runs from 2026-09-28 on)
├── pipeline_state.json                     # pipelines
├── lifecycle_seed_stage<N>/                # SDO pipeline reuse evidence
├── sdo_persistent_controller.json          # persistent-controller pipelines
└── stage_<N>_<name>/ or run root
    ├── experiment_config.toml
    ├── run_manifest.json                   # per stage, written when the stage starts
    ├── application_workspace/
    └── problem_runs/<problem-id>/
        ├── results_*.csv
        ├── agent/
        │   ├── sdo_production_receipt_strict.json
        │   ├── sdo_incident_resolution.json   # persistent-controller runs
        │   ├── sdo_rejected_production_receipt.json  # persistent runs whose drained receipt failed validation
        │   ├── detector_firings.jsonl      # controller firing telemetry (rotated file first), cumulative over a persistent pipeline
        │   ├── sdo_turn_usage.jsonl        # host-side lifecycle turns
        │   └── sdo_runtime/                # exported from the workspace PVC
        │       ├── usage/controller-turns.jsonl   # broker + reflection turns
        │       ├── usage/responder-turns.jsonl    # responder Job turns
        │       ├── telemetry/detector-firings.jsonl(.1)  # raw firing stream from the PVC
        │       ├── codex/sessions/YYYY/MM/DD/rollout-*-<session>.jsonl
        │       ├── claude/projects/...            # Claude provider only
        │       └── controller_logs/<pod>.log      # kubectl logs --timestamps of each sdo-controller-run pod
        └── <harness and agent logs>
```

`run_manifest.json` (`benchmarks/sregym/runner/manifest.py`, `schema_version` 1) is written by the runner at launch into the experiment directory, the pipeline directory and each stage directory. Its fields:

- `kind`: `experiment`, `pipeline` or `stage`.
- `codex_prompt_appendix`: for each `agent = "codex"` config, `mode` (verify protocol), `exec_disclosure`, `allow_exec` (true when SREGym's agent proxy forwards `kubectl exec`, attach and port-forward for that arm; phase-1 exec parity) and `sha256` of the appendix text.
- `git`: `sha`, `dirty` and `dirty_paths`, plus `submodule` with `sha`, `recorded_sha` and `dirty`.
- `images`: keyed by `<role>:<ref>`. Each entry has `id`, `repo_digests` and `id_at_preflight`; agent images also carry the probed `codex` and `agentshim` versions and `import_error`.
- `versions`: `codex_cli` (`pin`, `host`, `stock_arm`) and `agentshim` (`pin`, `host`).
- `models`: one mapping per arm or stage, from role to `provider`, `model`, `effort` and `source`. The roles are `responder`, `reflection`, `lifecycle_deployer`, `health_judge`, `baseline_agent` and `sregym_judge`.
- `judge`: `model` and `effort`.
- `kind_topology`: `clusters`, `worker_nodes` and the observed `nodes`.
- `config`: `snapshot`, `sha256`, `source` and `source_sha256`.
- `host`: `load_average`, `cpu_count` and `disk_free_bytes`.
- `codex_quota` and `lanes`.
- `preflight`: `ok`, `mode`, `waived`, `checks` and `facts`.

A resumed run keeps its first manifest and appends each resume's manifest under `resumes`. Runs from before 2026-09-28 have no manifest.

Classify runs before analyzing them: `uv run python -m benchmarks.sregym.analysis.run_validity <dir>... [--logs-root third_party/sregym/logs] [--legacy] [--json out.json]`. It labels each problem run:

- `invalid_infra`, with reasons, for a harness or host fault. The causes are: no manifest or a waived preflight; no result row; a failed CLI install; exhausted Codex quota; tokens that do not reconcile between rollouts, usage records and result files; a passed stage without judge-free TTD/TTM, or a TTM before the TTD; an isolation-guard mismatch or no guard; another lane's kind nodes in agent output; an acknowledged submission the harness never graded; or a stopped pipeline that never published a stage's deferred receipt.
- `agent_failure` for a real failure. The causes are: a failed oracle, `agent_error`, no valid SDO strict receipt, or leftover `sdo.dev/responder-helper=true` objects.
- `valid` otherwise.

A directory name prefix a person gave (`invalid_`, `sdobug_`, ...) is shown as `manual:` but never decides the class. `--legacy` accepts runs from before 2026-09-28: a missing manifest is noted instead of failing, and a missing guard is accepted when the run did not overlap another run in time. `incident_cost` applies the same classification and excludes `invalid_infra` runs, printing each one with its reasons. Pass `--legacy-runs` for pre-manifest runs, or `--include-invalid` to report every run.

Current SREGym parallel runs instead write each run under `runs/<6-digit sequence>_<problem-id>/worker_<N>/results/`. A problem listed several times in `runner.problems` (kept in order, e.g. A B C D A B C D) and each of the `runner.repeat` independent attempts (passed as `--n-attempts`, expanded consecutively as A A B B; fresh fault injection and agent launch, not retries) gets its own sequence number, so group rows by `problem_id` across sequences rather than assuming one directory per problem.

`controller_logs/` is written by the adapter's cleanup, so it also exists after a failed controller Job; an export failure is recorded in `controller_logs/export_error.txt` instead of failing the run. Each controller evaluation line (`controller_iteration`, `findings`) carries no timestamp of its own; use the `kubectl` timestamp prefix. The broker ledger's `closure.request.detector_history` is frozen when the incident opens and compacted to the last 12 evaluations, so evaluations after dispatch appear only in these logs.

Every structured agent turn appends one JSONL record to the file named by `SDO_TURN_USAGE_LOG`: host-side lifecycle turns to `sdo_turn_usage.jsonl` in the run's agent log directory, and in-cluster turns to `/workspace/.sdo-runtime/usage/{controller,responder}-turns.jsonl` on the workspace PVC, which the adapter exports to `agent/sdo_runtime/usage/` before building the receipt. Each record has `recorded_at`, `provider`, `model`, `cwd`, `session_id`, `resumed`, `duration_seconds`, `tool_calls`, `shell_commands` (count), `shell_command_lines` (the commands in order, each capped at 2,000 chars; absent in older logs), `model_requests`, `model_requests_source`, and `usage` (`llm_calls`; agentshim's normalized token breakdown `input_tokens` (including cache reads and writes), `cache_read_input_tokens`, `cache_write_input_tokens`, `cache_write_1h_input_tokens`, `uncached_input_tokens`, `output_tokens` (including reasoning) and `reasoning_output_tokens`; the deprecated alias `cached_input_tokens` (cache reads); and `model_requests` when known). Records written before agentshim 0.7 lack `cache_read_input_tokens`, and on Claude their `cached_input_tokens` also counted cache writes. `llm_calls` is agentshim's turn count: always 1 per Codex `exec` run, but Claude's agentic turns. `model_requests` is the per-request count: for Codex, `token_count` events with usage that this turn added to its session rollout (`model_requests_source=codex-rollout-token-count`); for Claude, its reported turns (`claude-num-turns`); `null` when the rollout could not be read. Cross-check against the exported Codex rollouts, whose `event_msg`/`token_count` entries carry per-request `last_token_usage`; a resumed session's rollout also contains the earlier turns. Current runtime-artifacts exports retained sessions under `sdo_runtime/sessions/<incident-hash>/{codex,claude}/`; they are retained for seven days after durable acknowledgment and pruned daily. Match reflection to the responder session ID when resume mode was selected.

Result CSVs may flatten stage results into fields such as `Diagnosis.success` and `Mitigation.success`. They also carry conductor wall-clock epochs `fault_injected_at`, `diagnosis_submitted_at`, and `mitigation_submitted_at` (recorded when the agent's `/submit` request arrives, before API retries or oracles) and, for agents with `defer_fault_injection`, `fault_injection_deferred_seconds`. Report timing judge-free for every arm: time to diagnosis is `diagnosis_submitted_at - fault_injected_at`, and the headline time to mitigation is `mitigation_submitted_at - fault_injected_at` minus the diagnosis-grading wait `fault_injected_at + TTL - diagnosis_submitted_at`, but never less than when the agent's last state-changing command before the mitigation POST completed (from the exported Codex rollout). The unadjusted `mitigation_submitted_at - fault_injected_at` includes judge time and is supplementary only (`raw_incl_judge_s`). The CSV's own `TTM` column additionally includes the mitigation oracle and is not a headline number. Runs with `defer_diagnosis_grading = true` carry `diagnosis_grading_deferred = true`: the diagnosis is graded by the same judge in the background while the mitigation stage is already open, so their grading wait is zero, `TTL` is measured at diagnosis submission, and the CSV's `TTM` no longer includes diagnosis judging; compare raw `TTM` only between runs with the same marker. Require explicit true values and inspect `agent_error`; missing or malformed values are not success.

For multi-stage SDO pipelines compared against stock Codex, `uv run python -m benchmarks.sregym.analysis.incident_cost <sdo-pipeline-dir> --codex <codex-dir>...` prints per stage `ttd_s` and the headline judge-free `ttm_s`; the supplementary `raw_incl_judge_s`, `no_judge_s` (raw minus the grading wait, which is zero for `diagnosis_grading_deferred = true` rows), `first_mut_s` and `last_mut_s` (first state-changing command issued, and last one completed, both from rollouts); cumulative `ttm_s`; `incident_resolution_seconds`; oracle verdicts, responder and reflection tokens (reflection kept out of resolution time), a token-breakdown table (uncached input, cache reads, cache writes and their one-hour part, output, reasoning, raw total, cost-weighted total, USD, model requests) for every SDO stage and baseline problem with the pricing table version and date it used (see "Token metrics" in `benchmarks/sregym/AGENTS.md`), receipt `memory_reuse.warm_path` beside whether the responder rollout's user prompt carried the warm-path instructions, `.sdo/` detector and playbook counts, and token break-even against the per-problem Codex mean with and without the one-time lifecycle (`sdo_turn_usage.jsonl`, or `--lifecycle-usage` for a seeded lifecycle).

## Agent trajectories

Generic CLI benchmark agents may emit JSON or JSONL trajectories under run-specific `agent/` or `trajectories/` directories. Their schema is agent-specific. Start by inspecting keys and timestamps rather than applying a historical fixed schema.

Use trajectories to explain hypotheses, commands, tool failures, and detours. Do not use them as substitutes for controller outcomes, broker commits, independent verification, or strict receipts.

## Detector firing telemetry stream

`agent/detector_firings.jsonl` (also `agent/sdo_runtime/telemetry/detector-firings.jsonl` and its rotated `.1`) is the controller's durable, append-only record of firing transitions, one JSON object per line with `schema_version` `sdo.detector-firing/v1`. It lives outside `.sdo/` and is not operational memory. Fields: `event_id`, `event` (`activated`, `cleared`, `not_persisted`, `batched`), `recorded_at`, `evaluation_iteration`, `application`, `namespace`, `detector_id`, `detector_class` (`health`/`incident`), `owner`, `rule_id`, `fingerprint`, `severity`, `parameter_bindings`, `surfaced_playbooks`, `firing_count`/`firing_threshold`, `clear_count`/`clear_threshold`, `incident_id` (empty when no incident is open), and `dispatch_relation`. An activation normally records `no_incident` (the batcher debounces) and a following `batched` record with the incident id settles `before_dispatch`. The stream is cumulative across a persistent pipeline, so scope by `incident_id` and time; a torn last line is possible after a crash, so skip unparsable lines. A `not_persisted` record with no later `activated` for the same fingerprint means the detector flagged the fault but it never met its firing threshold, which for a learned incident detector (required `persistence.firing: 1`) should not happen. `benchmarks/sregym/analysis/stream_curve.py` writes `detector_firing.csv` and the `incident_detector_fired_*`, `no_incident_detector_fired`, `fired_detectors` and `firing_telemetry` columns of `incidents.csv` from the receipt (falling back to the stream for incident ids); `firing_telemetry` empty means the run predates the telemetry.

## Incident lifecycle event stream

`sdo_runtime/telemetry/lifecycle-events.jsonl` (and its rotated `.1`) is the controller's durable, append-only record of its own incident lifecycle transitions, one JSON object per line with `schema_version` `sdo.lifecycle-event/v1`. Like the firing stream it lives outside `.sdo/`, is not operational memory, carries no benchmark labels or verdicts, is cumulative across a persistent pipeline (scope by `incident_id`), and may have a torn last line after a crash (skip unparsable lines). Absent in runs that predate it. It fills the lifecycle transitions the firing stream and outcomes never recorded, so an operator can reconstruct one incident end to end offline. Envelope fields match the firing stream (`event_id`, `event`, `recorded_at`, `evaluation_iteration`, `application`, `namespace`, `incident_id`); the `event` phases are `incident_opened` (with `finding_keys`, `surfaced_playbooks`, and for a follow-up `parent_incident_id` and `follow_up_attempt`), `workspace_prepared` (`worktree`, `base_commit`), `responder_dispatched`, `responder_completed` (`dispatch_error` when the responder Job failed terminally), `incident_superseded` (`superseded_by`, `reason`), `worktree_released` (`reason`), `detector_review_required` (`reason`), `incident_closed` (`health_cleared_at`, `detector_review_required`, `dispatch_error`), `closure_committed` (`proposal_commit`, `outcome_commit`, `reflection_commit` — join to the logical outcome by `outcome_commit` (individual JSON documents on active Go runs; JSONL in archived Python runs)), and `incident_acknowledged`. Each `(incident_id, phase)` occurs at most once and `event_id` is content-addressed over it (a supersede also mixes in the child id), so a crashed-and-restarted controller re-emits the identical id and the stream drops the duplicate. A follow-up is a distinct `incident_id` linked to its parent via `parent_incident_id`/`superseded_by`; walk that chain to follow a whole incident family. To reconstruct a timeline, filter both streams by `incident_id` and order by `recorded_at` (lifecycle phases break ties in lifecycle order); a missing `incident_closed`/`incident_acknowledged` after an `incident_opened`, or a `worktree_released` that never follows an `incident_superseded`, pinpoints exactly where a stuck incident or a stranded worktree stalled.

Native worker task/result payloads use logical `playbook_id`, `script_names`, and `proposed_artifact_ids`; a reflection result may include a typed detector/playbook `artifact_proposal`. Resolve those IDs through the accepted-commit memory catalog and broker commit when investigating learning. Old Python-run receipts may still contain `.sdo/` paths in `playbooks`, `scripts`, or `proposed_memory_changes`; treat these as legacy transport values rather than extra artifacts. The worker's proposed IDs are claims until the Go memory edge materializes them and the broker accepts the resulting diff.
