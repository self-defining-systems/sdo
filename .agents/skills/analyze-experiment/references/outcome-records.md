# Outcome and program evidence

## Outcome records

Phase-1 program memory stores responder-owned Go `diagnose.go`, optional `mitigate.go`, and tests beside judgement guidance in `.sdo/playbooks/<fault-class>/`. Shared helpers are under `.sdo/lib/<package>/`; labeled replay cases are under `.sdo/corpus/<case>/` with `open.json`, `fixed.json`, `healthy.json`, `recordings.json`, and `labels.json`. Reflection authors these files directly in its isolated checkout. The isolated broker validator and local `memory check` share compilation, generalization and rename-invariance replay; a program's presence alone does not show runtime use or a mitigation. Correlate any later program-use claim with controller outcomes and accepted commits.

For every new captured corpus case, including one for an existing program, `open.json` comes from one of the controller's application-namespace captures: `open@detect.json` (older runs may also have `open@settle.json` or `open@pre-apply.json`, which the controller no longer captures). Reflection selects a pre-mitigation capture phase and copies its bytes directly into the five corpus files, authoring labels with capture digests, bindings, peer bindings, and root-cause IDs. The shared Go validator verifies those bytes against the private capture directory; `labels.json` records the selected `provenance.open_at`. Each open capture has an adjacent `open@<phase>-recordings.json` for ReadView primitive calls. `fixed.json` is captured after verified closure, and `healthy.json` reuses the fixed snapshot with a same-kind peer binding. Captures live privately at `.sdo-runtime/sessions/<first-32-hex-of-sha256(incident_id)>/corpus/` until session pruning. Inspect `labels.json` `provenance.incident_id`, `open_at`, `open_sha256`, and `fixed_sha256` against the selected phase file and fixed file, and confirm the reflection commit passed broker validation. Sensitive environment values and Kubernetes write metadata are removed; inline synthetic NoMatch cases remain supported. An agent-authored near miss must carry `no_match_program_ids` and `synthetic_no_match_reason`; do not count it as observed incident evidence. Older accepted corpus cases may predate capture provenance; treat their open/fixed/healthy JSON as author reconstructions, not independent evidence of generalization. Shared `validate.Check` compares every added captured case against the provisioned incident and capture directory; missing context is `program.capture-unavailable`, and mismatched or empty incident labels and modified capture bytes are `program.capture-provenance`. Self-reported hashes alone do not establish capture provenance. Every accepted case is immutable against the accepted base commit (`program.corpus-immutable`): snapshots, recordings, provenance, bindings and labels cannot be rewritten or deleted. This also protects legacy and synthetic cases; unchanged historical cases do not need the current incident's capture mount. New evidence requires a new case ID, and relabeling accepted evidence is unsupported. Changed Go source must already be gofmt formatted; publication preserves authored bytes.

Reflection may instead return `learning_decision=sdk_gap` with typed `sdk_gaps` entries (`fault_class`, missing `primitive`, `reason`, and `scratch_script`). These are in the durable native broker ledger's `reflection_decision`, joined to the immutable outcome by incident ID and `outcome_commit`; they record a proven check the current SDK could not express, not an accepted program or repair. An `updated` decision may also carry gaps for other faults. For an accepted program, inspect the reflection commit's playbook sources and corpus labels, then the broker validation evidence; the proposal or program self-check result alone does not prove acceptance.

An exhausted model-output correction returns a failed worker result. The native ledger then records `reflection_decision.learning_decision=failed` and `reflection_decision.error` with the validation reason, sets `reflection_processed=true`, and completes closure without a reflection commit. The already committed successful outcome remains the mitigation record. A repeated identical worker request is not evidence of three distinct learning attempts; check the worker result and broker ledger separately.

The logical outcome schema is `OutcomeRecord` in `sdo/contracts/proto/sdodev/contracts/v1alpha1/outcome.proto`. The active Go memory adapter stores one versioned JSON document per incident at `.sdo/outcomes/<sha256(incident_id)>.json`; its logical `Reader` lists and gets records by incident ID, while only the broker has `Writer` capability. Reflection tasks carry the accepted current and prior outcomes as typed protobuf records. The adapter can import a retired `.sdo/outcomes.jsonl` stream and removes that stream only after every record is accepted. Correlate incident IDs and outcome commit hashes with the native broker ledger and benchmark `production-receipt/v2`. Important fields include:

- `incident_id`, `source_commit`, `deployed_commit`;
- `drift_events` retain controller-observed refs, bounded old/source/new fields, manager/operation/time and `classification` (`fault` for a learned match, otherwise `unexplained`). Current ordinary responder results may return exact event assessments with legacy `investigation_verdict`, `investigation_reason` and `investigation_evidence` spelling. Go validates them against incident observations; a bug requires source contradiction plus relation or impact evidence. Only checked benign labels in accepted outcomes suppress the identical manager and current/source observation after restart/reset. Bug and unsure never suppress repeats. A benign no-op is `cleared_without_action`, with no mitigation/trust/learning credit. State retains bounded history, not investigator requests, verdicts or drift admission accounting. Health and every retained synthetic drift finding must clear; source errors, missing bindings and Unknown remain unresolved. Learned deletion needs explicit NoMatch per retained binding. Ordinary captures use the incident session's `open@detect` phase. Ownership adoption retains counts, managers and retry diagnostics. Historical runs may contain investigator state and a separate verdict ConfigMap; current releases remove both.
- detector history, findings, and final health-detector state;
- surfaced, inspected, confirmed, rejected, and applied playbooks;
- confirmed root causes. Newer results give each cause `evidence` (live items only: `detector-finding`, `synthetic-traffic`, `state-change`, or `live-observation`, each with `source` and `observation`), `explained_detectors` (detectors that must clear after the fix), and `static_context` (scripts, manifests, ConfigMap bodies, or notes that motivated the hypothesis but prove nothing). Older records have these empty;
- `diagnosis_verification` (absent in older records): per root cause, SDO's deterministic `verdict` (`confirmed`: a detector flip or a recorded latent-cause check backs an attributed repair, and no cited evidence is contradicted; `contradicted`: some cited detector, scenario, or state change was never observed by the controller, the signature of a red-herring diagnosis; `unverified`: no contradiction but no causal check passed; `unattributed` (absent in records before repair attribution): a causal check passed, but the responder's own repair does not back the cause; `no-evidence`: a legacy cause), the per-item `evidence` checks (`verified` true, false, or null for unverifiable live observations, and `reason` (absent before rc2) when a reference existed but is not evidence), the `detectors` flips, and `repair` (absent in records before repair attribution): `attributed`, the backing `actions` (IDs of successful repair actions that started by the closure's `health_cleared_at` and touched the cause's resources), `repaired_resources` (`Kind/name`), `externally_reverted` (dispatch-diff objects gone from `final_state_changes` that no responder repair touched), and a `reason`. A cause is attributed when such an action touched one of its resources (or a `state-change` object it cites) that was in the dispatch diff; a cause whose touched resources are not in the dispatch diff (a runtime fault, a late composite component, or a restarted workload) is attributed only when `externally_reverted` is empty. Each cause of a composite is attributed to its own repair, so with one repaired component only that cause is `confirmed`. `unattributed` means someone else most likely fixed the fault inside the verification window while the responder claimed a wrong cause; A `state-change` source resolves `Kind/name` and `Kind/<incident namespace>/name` to the same controller-observed object for observation, baseline restoration, and repair attribution. A different namespace stays unverified with an explicit namespace-mismatch reason; compound references remain invalid. A `state-change` evidence check is verified against the union of `request.state_changes` and `final_state_changes` (see the broker ledger below), so a cause citing a composite's late-landing fault is not `contradicted` merely because it missed the dispatch-time snapshot; when the closure carries `observed_state_changes` (rc2), a citation outside the dispatch diff must instead appear there with a `first_observed_at` earlier than the start of the responder's first repair action on that object, otherwise it is `verified: false` with a `reason` naming that action (the responder cited its own edit, such as a restart's `restartedAt`), and a late fault the responder reverted exactly still verifies from that record;
- Newer latent-cause checks add `program-verdict` evidence when one program and binding has a pre-fix `Match` and post-fix `NoMatch` under verified health, or `baseline-restoration` evidence when a cited changed field on a repaired object returns to the controller's healthy baseline in a final observation after the successful repair. Either can confirm an attributed cause even if its explained detector never fired. Read each check's `reason`; baseline restoration proves equality to the recorded healthy state, not independently to an accepted source manifest.
- `classification`: `success`, `partial` (an incomplete closure: health was unverified or diagnosis lacked independently confirmed evidence; never receipt accepted or learned), `external_recovery` (health cleared in time, but every cause is unattributed, so the recovery is not credited to SDO; `verified_at` is still set), `false_positive`, `false_negative`, `failed`, `cancelled`, or `cleared_without_action` (health verified clear, but the responder made no successful change, whether it reported `completed` or `cancelled`; older records classed the `completed` case as `cancelled`; it is not a mitigation). The single classification list in `outcome.proto` governs the generated contract; successful outcomes alone are learnable. A verified finding plus a detector that fired and cleared can confirm a cause even when supplemental live-observation evidence is not independently verifiable; an explicitly contradicted check still blocks confirmation. The broker never reflects on `partial`, `external_recovery` or `cleared_without_action`, and the controller never surfaces them, or a `contradicted`/`unattributed` cause of a `success`, as prior-outcome evidence;
- repair and memory commits, plus structured live repair-action receipts; newer receipts carry `resources`, the objects each action mutated (older ones only a free-form `target`, parsed as `[namespace/]Kind/name` when possible);
- responder backend/model and transport-reported usage (`llm_calls`, `input_tokens`, `cache_read_input_tokens`, `cache_write_input_tokens`, `cache_write_1h_input_tokens`, `uncached_input_tokens`, `output_tokens`, `reasoning_output_tokens`, `model_requests`, and `total_cost_usd` when the provider reports it). `cached_input_tokens` is the deprecated alias of cache reads; a record without `cache_read_input_tokens` predates agentshim 0.7, and on Claude its `cached_input_tokens` also counted cache writes (subtract `cache_write_input_tokens` to get reads);
- detected, dispatched, mitigated, verified, and completed timestamps.
- `program_tool_calls` (command, time, request and response JSON, error), `program_runs` (program ID, finding fingerprint, binding source, bindings, verdict, duration, program revision, optional `can_mitigate`), and `plan_applications` (application ID, program IDs, plan, applied/dry-run flags, verification, error, duration, rollback state, pre-images, applied actions, patches and timing). `binding_source` is `finding`, `hint`, or `sweep`; sweep runs have no finding fingerprint. Older runs omit this field. `response_loops_used` counts apply batches; `response_loop_exhausted` marks an unresolved budget stop. `program_failure_signals` distinguishes a matching diagnosis after apply, residual detector findings, newly surfaced findings, and ad-hoc coverage gaps. Read the [program trust rules](fastloop-results.md#program-trust-evidence) before counting successes. Fast-path execution is opt-in; infer actual use from `resolution_path` and the native ledger.

Tool responses expose logical playbook IDs. The outcome keeps a structured summary with `truncated: true` when a full tool response would exceed 2 KiB. A clean `verify` omits the unrelated namespace sweep. For verified repairs, `timestamps.mitigated_at` is the last successful repair completion no later than the final health-clear streak, falling back to that clear time when no completed repair receipt exists.

When a responder completes but the health detectors do not clear within the controller's verification window, the controller closes the incident with empty `final_detector_states`; the outcome is classified `failed`. Do not read that closure as verified health.

Useful queries for the active per-incident outcome documents:

```bash
jq -s 'map({incident_id, classification, repair_commit, memory_commit, diagnosis_verification})' .sdo/outcomes/*.json
jq -s 'group_by(.classification) | map({classification: .[0].classification, count: length})' .sdo/outcomes/*.json
```

The filename is a hash, not an incident ID. For a historical checkout containing JSONL, inspect its accepted Git revision and import state before combining counts.

Program-run `can_mitigate` records whether the compiled registry has a mitigator; `false` means diagnosis-only, and an absent field on older evidence means unknown. It does not establish trust, plan validity or replay support. Responder prompts omit NoMatch runs and report `omitted_no_match_program_runs`; durable requests, outcomes and captures retain the full runs.

Current reflection workers can materialize positive cases through the typed `create_corpus` tool. It copies the controller open/fixed/recording bytes and derives phase values and SHA-256 provenance; it does not grant acceptance. The broker still compares the proposed bytes independently. The typed `check_memory` input is unwrapped ReflectionResult fields; the final model reply retains the session envelope with `reflection` populated and `incident_result` null. The generated worker guide is `sdo/skills/sdo-memory/references/runtime.md`; generated program API documentation is `sdo/skills/sdo-playbook-authoring/references/program-sdk.md`.

Reflection evidence browsing is a bounded projection only: inventory and field pages carry the accepted outcome commit, incident ID and capture digests. Oversized page items require narrower field selection, not a conclusion that evidence is absent. Full captures and the committed outcome remain authoritative. Prompt memory inventories excerpt accepted text and omit script bodies; accepted files remain in the proposal checkout.
