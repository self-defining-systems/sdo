# Structured plan authority

The installation administrator supplies `plan_safety_policy_json` and its separately reviewed `plan_safety_policy_sha256` in the controller's typed launch config. `install.Config.PlanSafetyPolicyJSON` / `PlanSafetyPolicySHA256` and the controller launch flags of the same names carry these values into `RuntimeOptions.PlanSafety`. Unconfigured controllers refuse structured actions. The `host`, `operate`, and `install-existing` commands accept `--plan-safety-policy-json` and `--plan-safety-policy-sha256`; `--plan-webhook-name` additionally grants only that exact webhook name. Operate Jobs preserve these administrator inputs through controller installation. Installer hash mismatch fails before resources are applied.

The original fixture-document mode accepts only `authority: "reviewed-fixture"`; the source-only stream mode is described below. A reviewer establishes the nonsecret consumer, identity and routing closure before approving any opaque read. The document contains `review_id`, `source_commit`, RFC3339 `expires_at`, and `objects`: records with `ref`, live `uid`, approved `digests`, and explicit `create_allowed` / `delete_allowed` flags. Missing-object creates may omit UID; deletes always require an exact live UID. Optional `service_accounts` records pin independently reviewed powerless account refs and UIDs. Refs use the SDK ObjectRef JSON shape. Duplicate refs, invalid digests, expired documents and unknown fields refuse at startup.

Each digest is calculated with the controller's `ReviewedPlanObjectDigest` from an independently reviewed fixture image. The set must include allowed pre-images and allowed resulting images. A source-derived fixture must be reviewed for credential and routing effects before its digest is approved: source origin alone grants no authority. Arbitrary responder-chosen values outside this set refuse. The runtime never derives approvals from the proposed plan, dry-run images, patches, receipts, current opaque objects, or responder attestations. The administrator-controlled launch config and separately pinned hash are the trust boundary; changing either is a new administrative authorization, not an agent operation. Do not place this authority in responder-editable source or forward it into worker task input.

To enable a stream fixture, its operator reviews the exact object/UID and finite allowed source/repair images, pins the resulting document hash in launch config, and chooses an expiry beyond the run. The policy is bound to that accepted commit; a changed commit requires review and controller configuration again. This finite reviewed-fixture mode deliberately does not authorize unconstrained new LLM values. A policy document claiming dry-run authority, a raw dry-run result, or bytes differing from the administrator-pinned hash cannot populate the policy.

## Accepted-source stream policy

The committed `sdo/operator/config/plan-policies/mixed10.json` reviews exactly the astronomy-shop, hotel-res and social-network application namespaces. It contains no literal repair values. This authority mode is generated per incident from the controller's accepted render and admitted incident findings, never from responder actions, dry runs, or hashes of current opaque objects. Source manifests supply independently authorized repair values and named create identities. Source-absent deletes must be individually named by an incident finding and pinned to the object's UID through a metadata-only current read. Only the configured policy/webhook kinds are eligible; webhook RBAC remains exact-name installer authority. No kind-wide deletion is generated.

The reviewed policy authorizes reading nonsecret source-owned application objects in those namespaces; the full credential/routing predicate remains mandatory on source and live images. Unsafe source objects are excluded. Faulted pre-images do not need an exact healthy-image digest: effect authority comes from restoring the selected accepted-source value, checked independently for each structured action. The generated policy is incident-bound, expires, pins current UIDs, and is cached for that incident so recreation cannot refresh delete authority. CreateFromSource uses the accepted source object; compensation retains the original captured image.

Legacy SetField paths retain their existing literal values and universal post-image credential delta. They do not acquire the source-only restriction. Receipts distinguish `accepted-source`, `incident-named-delete`, and `legacy-literal` so analysis can separate those repair classes. Values outside accepted source are never authorized through the structured stream-policy path.

RH3B/ST3 launch input: set `SDO_PLAN_SOURCE_POLICY_FILE` to the absolute path of `sdo/operator/config/plan-policies/mixed10.json` in the frozen checkout before invoking the launcher. The existing Go `host`, `operate`, and `install-existing` entry points consume it; alternatively pass `--plan-source-policy-file PATH` explicitly. They embed the bytes in `install.Config.PlanSourcePolicyJSON`, then `ControllerConfig.plan_source_policy_json`, so no host file mount is needed inside the controller. Explicit `--plan-source-policy-json` is the embedded transport. The policy also supplies only `pod-policy.validation.k8s.io` for the installer's existing exact-name webhook get/delete grant; controller-generated delete authority still needs that name in the incident, source absence and the pinned UID. No benchmark adapter edit is required for the environment input, and no authority is passed to responder workers.

Generation runs when the controller constructs the incident responder loop, before responder plan output exists. A metadata-only identity epoch is cached for that incident; later requests and dry runs cannot refresh UIDs. The generator uses no fault catalog or benchmark verdict. The committed namespace/kind/name configuration is the reviewed authority; a launch hash is only transport integrity, since an administrator able to edit launch configuration controls both bytes and hash. Credential-bearing or otherwise forbidden source/live images continue to refuse even within the configured namespaces.
