# SDO architecture

This document describes the production boundaries implemented in this repository and the separate SREGym benchmark boundary. It does not treat historical deployment experiments as production features.

## End-to-end lifecycle

```text
human health objective
        |
        v
agent proposal in isolated checkout -> trusted source build/apply/readiness -> broker commit
        |
        v
source-grounded architecture proposal -> broker commit
        |
        v
fresh health-judge proposal -> isolated detector validation -> broker commit
        |
        v
controller builder/install -> deterministic Go controller -> incident batch
        |
        v
registered responder job -> independent verification -> broker outcome commit
        |
        v
fresh reflection proposal -> broker validation/commit -> controller rollout
```

`sdo-operator host` starts the active production lifecycle; the installed `sdo-operator operate` continues it in the cluster. Go coordinates separate Human goal, Upkeep schema, Deployer source and architecture, and HealthJudge bootstrap proposals. The source stage requires a trusted deployment receipt bound to the exact candidate Git tree and immutable running images before publishing; architecture cites the broker-returned accepted source commit. The controller then runs deterministic detectors, dispatches registered incident workers, independently verifies recovery, records the outcome, and dispatches reflection. A full host-to-controller kind smoke passed with live clear detector evaluations; deployment still depends on the target cluster, registry, credentials, and application manifests.

## Component boundaries

Go owns operational decisions and accepted repository state. Python hosts the built-in agent implementations. Registration is implementation neutral: a versioned ProtoJSON `AgentRegistration` advertises an agent ID, capabilities with exact protobuf request/result type URLs, and a launch method. `AgentTask` and `AgentResult` carry typed protobuf `Any` payloads and a proposal workspace. The Go registry rejects unknown IDs, capabilities, and payload types; the generic Kubernetes executor launches a registered worker without knowing its language or model provider. Built-in manifests live in `sdo/agents/registrations/`; third-party workers can use another language if they honor the same contract. Incident, lifecycle, and reflection dispatch use this boundary.

The `.proto` files are the source of truth for messages crossing Go, Python, and worker boundaries. The controller retains its own live state structs for scheduling and persistence, then explicitly projects them into generated protobuf request, result, and closure messages. Outcome derivation constructs generated outcome messages directly. The built-in Python workers parse and build the generated messages directly; the only hand-written model-output schema is the thin `_incident_result_schema` in `sdo/agents/responder/codex.py`, pinned to the `IncidentResult` descriptor by a parity test. The controller's persisted state (the runtime-state ConfigMap) and the broker ledger are canonical ProtoJSON of `ControllerState` and `BrokerLedger`; the Go structs in `runtime/protocol.go` carry no JSON tags and convert through `runtime/contract_projection.go`. The incident view published for Python and benchmark readers is a ProtoJSON `IncidentView`. Canonical ProtoJSON omits empty fields, so readers tolerate absent keys. Reflection consumes generated outcome messages directly. Dynamic finding metadata is the only field in the Go incident projection that needs a JSON value conversion. Conformance tests cover the projections and reject contract drift.

Native incident and reflection tasks carry an accepted-commit-bound `OperationalMemorySnapshot` with goal and architecture text, logical detector registrations, and playbook IDs/content. Agents return logical IDs and typed `OperationalArtifactProposal` mutations for detectors, playbooks, and judge-owned traffic. The Go memory edge maps those proposals into repository files; the broker then validates role ownership, provenance, the actual diff, and independent test evidence before commit. Source repair still occurs in an isolated proposal checkout. Workers do not read or write physical operational-memory paths.

| Package | Responsibility |
|---|---|
| `sdo/agents/{deployer,health_judge,responder}/`, `sdo/agents/views/` | Built-in agent sessions, prompts, local provider adapters, worker entry points, and the reflection artifact draft; native memory reads and writes use logical protobuf contracts |
| `sdo/agents/lifecycle/` | Shared source architecture and health judge agent prompts and DTOs |
| `sdo/contracts/proto/sdodev/contracts/v1alpha1/`, `sdo/contracts/`, `sdo/operator/contracts/` | Shared protobuf schema and generated Python/Go messages |
| `sdo/operator/worker_registry/` | Strict registration, capability lookup, and implementation-neutral Kubernetes execution |
| `sdo/operator/lifecycle/`, `deployment/`, `artifacts/` | Go lifecycle decisions, trusted deployment/readiness strategies, and physical bootstrap-artifact writes |
| `sdo/operator/broker/`, `memory/` (including `memory/layout` and `memory/validate`), `outcome_derivation/` | Go commit authority, logical snapshot and artifact materialization edge, the single operational-memory validator, outcome store with physical JSON adapter, and controller-derived typed outcomes |
| `sdo/operator/{sdk,core,runtime,builder,install}/` | Detector SDK, deterministic execution, controller state and its typed contract projection, builder/supervisor, and Kubernetes installation |
| `benchmarks/sregym/` | First-party benchmark adapter, protocol, runner, experiments, and analysis |
| `third_party/sregym/` | External benchmark harness Git submodule |

Production packages do not import SREGym code. Benchmark adapters may call production APIs; strict receipts and submission relays remain in the benchmark boundary. The native path passed an end-to-end kind smoke with real goal/source/architecture/judge artifacts, concrete deployment and health evidence, provider credentials, and controller installation. Detector SDK staleness/dependency interface changes are outside this refactor.

## Controller

The controller is split by stability and privilege:

| Package | Responsibility |
|---|---|
| `sdo/operator/sdk/` | Public Go interfaces for detector specifications, snapshots, findings, persistence, batching, and test snapshots |
| `sdo/operator/sdk/servicehealth/` | Zero-knowledge ready-endpoints detector that names the selector labels a Service's backing Deployment lacks |
| `sdo/operator/sdk/traffic/` | Synthetic-traffic scenarios, parameter generators, workload profiles, the deterministic engine, sliding-window SLO evaluation, and the scenario SLO detector |
| `sdo/operator/core/` | Detector execution, snapshot validation, finding emission, and playbook-path validation |
| `sdo/operator/runtime/` | Kubernetes cache, scheduler, finding state, batching, responder jobs, broker effects, leader election, durable state, and the prober pod and its observer |
| `sdo/operator/runtime/prober/` | The isolated synthetic-traffic prober process (no Kubernetes dependency): continuous health probes, verify bursts, HTTP API |
| `sdo/operator/builder/` | Validate `.sdo/diagnostics`, compile detector and traffic-generator tests in isolation, and generate the application-specific controller and prober workspaces |

Generated detectors are deterministic Go. They consume controller snapshots and must not call models, read hidden benchmark labels, or use external verdicts.

### Synthetic traffic

The health judge writes Go generators (`.sdo/diagnostics/traffic/generators/`, a package exporting `Scenarios() traffic.Catalog`) and workload profiles (`traffic/workloads/<name>.yaml`). A scenario is a user journey: steps whose endpoints build requests from a seeded rng and per-iteration state and check responses, the Services on its request path (from `.sdo/arch.md`, for localization), a side-effect class (read, idempotent write, or write with cleanup steps), a synthetic-data marker for writes, and the fault classes it must detect. A workload is data: purpose (`health-probe` runs continuously and feeds a traffic health detector; `verify-burst` and `journey` run on demand for a bounded time), scenarios and weights, arrival pattern and rate, timeouts, and per-scenario SLOs. Its schema is defined once in `sdo/contracts/proto/sdodev/contracts/v1alpha1/traffic.proto` and code-generated for both sides; protovalidate CEL carries the invariants that do not need a Go-duration parse (duration bounds stay host code).

The `traffic.Engine` owns scheduling, arrival, rate, in-flight and time caps, latency measurement, and seeding: iteration *n* of a workload always builds the same requests, so any failing probe replays exactly. It refuses unsafe requests (writes from read scenarios, writes without the marker) without sending them. The builder compiles generators only into a separate prober binary (`cmd/prober`, with workloads embedded), never into the controller; generated tests prove that every scenario fails against simulated unreachable and 5xx targets plus its declared classes, that workloads name provided scenarios, and that traffic detectors consume health-probe workloads, and a static guard rejects generator imports that reach the network, filesystem, or cluster and package-level clock or rng calls.

The controller runs the prober as a pod in the control namespace: no service-account token, a read-only mount of only its content-addressed binary on the repository volume, CPU and memory limits, restart on crash, and a NetworkPolicy allowing egress only to the application namespace and cluster DNS. An unchanged binary keeps its pod across controller relaunches. The controller polls the prober's windows every 500 ms and wakes the traffic detectors only while a failure is inside a scenario's window; a scenario judges health only after it has succeeded once, and an unreachable prober surfaces as a detector error that blocks closure but never opens an incident. The always-on `service-endpoints` detector needs no authoring.

## Operational memory

The application repository is the shared durable memory. Five artifact classes live under `.sdo/`:

| Artifact | Owner | Contract |
|---|---|---|
| `goal.md` | Human | Application identity and exact health objective |
| `arch.md` | Deployer/upkeep | Source commit, topology fingerprint, and complete architecture summary |
| `playbooks/` | Responder | Fault-specific diagnosis, repair, and verification procedures |
| `diagnostics/` | Health judge and responder | Health and incident detector source, tests, module, and manifest; synthetic-traffic generators and workloads (judge-owned, except responder-owned `traffic/generators/incident/` and `traffic/workloads/incident-*.yaml`) |
| Outcomes | Controller through the broker | Immutable, versioned incident outcome documents and evidence |

The logical outcome contract is `OutcomeRecord` in `sdo/contracts/proto/sdodev/contracts/v1alpha1/outcome.proto`. The controller derives it, the broker alone receives `memory.Writer`, and `memory.Reader` exposes `Get` and `List` by incident ID. Reflection receives the accepted record and prior records as typed protobuf fields. The Go JSON storage adapter alone maps an incident ID to `.sdo/outcomes/<sha256(incident_id)>.json`, stores the versioned document, and can import the prior `.sdo/outcomes.jsonl` stream once, deleting that stream only after every record is accepted. Consumers never infer physical filenames. Broker-owned source deployment evidence lives outside `.sdo/` in its own durable ledger and is bound to an accepted commit.

`sdo/operator/memory/layout` is the only Go package that knows these physical paths: it owns the path constants and builders, `Classify(path)` (kind, ID, ok), the per-kind parsers and typed `Tree`, and the single detector manifest type. Each detector carries its own `manifest.yaml` at `.sdo/diagnostics/detectors/<health|incidents>/<id>/manifest.yaml`; the directory name is the detector ID. Schema version 2 introduced this layout; a version 1 repository (single `.sdo/diagnostics/manifest.yaml`) is converted by `layout.Migrate`, which the Upkeep actor commits through the broker. The controller does this at every start (operation `memory-v<N>-schema`, idempotent) before its first memory read, and `operate` does it as its schema step.

`sdo/operator/memory/validate` is the one validator for `.sdo/`. `validate.Validate(ctx, Request{Root, Base, Actor, Phase, Layers})` returns `[]Diagnostic{Rule, Path, Line, Message, Hint}`; validation failures are diagnostics, and the error result is reserved for infrastructure failures (unreadable files, a missing toolchain, a bad request). Rule IDs are stable strings such as `layout.unknown-path`, `manifest.parse`, `ref.unknown-playbook`, `ownership.denied`, and `detector.compile`. Four layers can be selected independently:

- **Structural**: every `.sdo/` path classifies through `layout.Classify`; no symlinks, secret-bearing names, or files over 256 KiB; YAML, front matter, manifests, and Go syntax parse; `schema-version` is current. Changed source files outside `.sdo/` are syntax-checked too.
- **Semantic**: ID patterns, unique detector IDs, `possiblePlaybooks` that resolve, playbook front matter, a complete playbook index, scripts that are executable, syntactically valid, and named by their playbook, no physical `.sdo/` paths in the architecture, playbook index, playbooks, or scripts, and an initial architecture that cites the accepted source commit. Completeness (goal, architecture, at least one playbook and detector) is required except in the bootstrap stages before the health judge.
- **Ownership**: computed from the diff against `Base`. The policy is one declarative table of kind by actor by phase (`grants` in `ownership.go`) plus diff rules for detector provenance, protected detector classes, Upkeep schema migrations, and the one-file architecture stage. The broker no longer has its own path-prefix checks.
- **Compile**: detectors build against the SDK, pass `go vet`, and pass their own tests, reusing the builder's detector workspace. It executes detector code, so it runs only in the network-isolated validation Job (`sdo-operator validate`), after the other layers pass.

The broker's `validateCandidate` runs the structural, semantic, and ownership layers in its staged clone and rejects with the diagnostics in the error; the Kubernetes validation Job then runs the compile layer through the same entry point.

`sdo-operator memory` (`operatorcli/memory*.go`) is the same validator and layout for agents and tools. `memory check [--root] [--actor] [--phase] [--base] [--layers] [--json]` runs `validate.Validate` (actor and phase default to `SDO_ACTOR` and `SDO_PHASE`; the default layers are structural and semantic, plus ownership when `--base` is set) and exits 0 when clean, 1 with diagnostics printed as `path:line: rule: message (hint)`, and 2 on infrastructure or usage errors; `--json` prints a `MemoryCheckReport` of `MemoryDiagnostic` messages as ProtoJSON, converted once in `validate.Diagnostic.Proto`. `memory ls` lists artifacts by logical ID from the layout tree, `memory new playbook|detector <id>` scaffolds a minimal artifact from `layout` writers and the one `DetectorManifest` type that passes `memory check`, and `memory outcomes` prints stored `OutcomeRecord`s, which is how the SREGym assurance harness and analysis read outcomes without recomputing `.sdo/outcomes/<hash>.json`. `broker/parity_test.go` runs a table of good and bad trees through both `memory check` and the broker's static validation and requires identical diagnostics.

Responder traffic: responders own incident-scoped traffic (`traffic/generators/incident/` and `traffic/workloads/incident-*.yaml`) in the reflection phase, and the health judge owns all other traffic. This is the broker's long-standing behavior and what the ownership matrix below documents. The retired typed `OperationalArtifactProposal` path (`memory/artifact_proposal.go`) rejected responder traffic outright; it does not define ownership and is being retired together with `MaterializeArtifacts`.

`schema-version` and `lifecycle-provenance.yaml` are validation metadata. They do not change the five ownership classes. Lifecycle provenance may attest an exact diagnostics-tree digest against an immutable validator image identity; only that exact pair can reuse a prior successful compilation, while any detector or validator change forces isolated validation again.

### Detector firing telemetry

The controller records, per finding, whether and when each detector fired. The runtime appends `activated`, `cleared`, `not_persisted` (flagged but gone before the detector's firing threshold) and `batched` (the activated finding joined a dispatched incident) records to a JSONL stream, `detector-firings.jsonl`, in the controller's durable runtime area on the repository PVC (`/workspace/.sdo-runtime/telemetry/`, `--firing-telemetry-path`, default on in job mode). It is operational telemetry, not operational memory: it is outside `.sdo/`, changes none of the five artifact classes or their ownership, carries no benchmark labels or verdicts, and is derived only from the controller's deterministic finding state. Each record has the detector id, class, owner, rule id, fingerprint, severity, parameter bindings, surfaced playbooks, firing/clear counts against the persistence policy, the evaluation iteration, the open incident id (empty if none), and `dispatch_relation`: `before_dispatch` (part of the dispatched batch), `after_dispatch` (activated while the responder was in flight) or `no_incident`. Because the batcher debounces, an activation usually records `no_incident` and a later `batched` record settles `before_dispatch`.

Event ids are a hash of the detector, fingerprint, event kind and a per-finding transition counter kept in the durable controller state, so a replay after a crash between emitting and persisting reproduces the same ids and the sink drops the duplicates; an ordinary restart restores the counters and emits nothing. The file is bounded (4 MiB, rotated once to `.1`, so at most 8 MiB), a torn last line is repaired on open, and a stream left over from an earlier controller lifecycle is archived as `.prev` when no state is restored. Sink failures are reported and never stop the evaluation loop.

The controller also keeps a compact timeline in its state and puts it in the incident closure as `detector_timeline` (per finding: `first_activated_at`, `last_seen_at`, `cleared_at`, `relation`, bindings, `surfaced_playbooks`) with three derived booleans: `incident_detector_fired_before_dispatch`, `incident_detector_fired_after_dispatch`, and `no_incident_detector_fired` (only health detectors fired). `IncidentClosure` carries them and the broker validates them and the SREGym adapter copies them into the strict receipt (`detector_firing_available`, `detector_timeline`, the booleans), exports the stream into the stage results as `detector_firings.jsonl` and `sdo_runtime/telemetry/`, and `stream_curve` reports them per incident. They distinguish a learned incident detector that fired before dispatch (memory used) from one that never fired (memory unused).

### Incident lifecycle event stream

The firing stream records whether and when detectors fired; the incident lifecycle event stream records the controller's own lifecycle transitions, so an operator can reconstruct a single incident's full timeline offline. It is a second durable, append-only JSONL stream (`lifecycle-events.jsonl`, `--lifecycle-telemetry-path`, default on in job mode) in the same runtime telemetry area (`/workspace/.sdo-runtime/telemetry/`), sharing the firing stream's durability mechanism: a bounded 4 MiB file rotated once to `.1`, a torn last line repaired on open, a stream from an earlier lifecycle archived as `.prev` when no state is restored, and content-addressed event ids that make a crash-replay between emitting and persisting idempotent. Each line carries the same envelope as a firing record (`schema_version` `sdo.lifecycle-event/v1`, `event_id`, `event`, `recorded_at`, `application`, `namespace`, `incident_id`) plus phase-specific fields. The `event` phases fill the transitions that previously emitted nothing: `incident_opened` (with `finding_keys` and, for a follow-up, `parent_incident_id` and `follow_up_attempt`), `workspace_prepared` (`worktree`, `base_commit`), `responder_dispatched`, `responder_completed`, `incident_superseded` (`superseded_by`, `reason`), `worktree_released`, `detector_review_required` (`reason`), `incident_closed` (`health_cleared_at`, `detector_review_required`), `closure_committed` (`proposal_commit`, `outcome_commit`, `reflection_commit`, which join the logical outcome by incident ID or outcome commit; the active Go memory edge stores per-incident `.sdo/outcomes/*.json`), and `incident_acknowledged`. Two further phases record load-aware admission when it is enabled: `admission_deferred` (a ready batch was held under resource pressure, with `load_pressure`, `load_threshold`, `release_backlog`, and a `reason` of `load_above_high_watermark` or `release_backlog_above_high_watermark`) and `admission_resumed` (the held incident cleared both low watermarks and proceeded to dispatch). Each `(incident_id, phase)` pair is emitted at most once, so its id is `sha256(incident_id, phase)` (a supersede also mixes in the superseding child id); a follow-up is a distinct incident id linked to its parent through `parent_incident_id`/`superseded_by`. `sdo/operator/runtime` stays transport-neutral: every field is a controller-internal fact (incident ids, git commit shas, worktree paths, finding keys), carrying no benchmark labels or verdicts, and the stream is derived only from the controller's deterministic lifecycle state. `ReconstructIncidentTimeline` joins the lifecycle and firing streams by incident id into one deterministically ordered timeline for offline analysis, and the record-and-replay harness pins that reconstruction against frozen artifacts.

#### Load-aware admission (overload backpressure)

The controller admits one incident at a time; a ready finding batch used to open an incident immediately and race the (possibly congested) close-out/drain of the previous incident. Under sustained host load that race widened into strict-receipt and stranded-worktree anomalies. Load-aware admission (default off; `--admission-load-high`/`--admission-load-low`, `--admission-release-backlog-high`/`--admission-release-backlog-low`, `--admission-recheck-interval`, `--admission-pressure-path`) gives the open transition explicit, deterministic backpressure. Two independent pressure terms, each with high/low-watermark hysteresis so the decision cannot flap: host load (an injected `LoadGauge`; production reads Linux PSI `/proc/pressure/cpu` "some avg10" through `ProcPressureGauge`) and the controller's own stranded-worktree release backlog (`len(pendingReleases)`, pure controller state tying admission to the drain path). When either term reaches its high watermark a ready batch is **deferred, not dropped**: the incident opens (keeping its identity and still coalescing later findings) but is held in `dispatchState = admission_deferred` before any worktree or dispatch, and resumes only when both terms fall below their low watermarks. The gauge and clock are injectable, so an admission trajectory is fully deterministic and testable with no wall-clock flakiness; a gauge read error fails open (admit). `sdo/operator/runtime` stays transport-neutral — every recorded field is a controller-internal load fact, no detector/LLM is involved — and the decisions are observable through the lifecycle stream's `admission_deferred`/`admission_resumed` phases.

#### Late findings (pull-before-act)

The incident request is immutable once the responder launches, so a detector that activates later cannot join the original batch. With `--late-findings pull`, the Go controller maintains a bounded per-incident report in a controller-owned ConfigMap. The incident worker receives only that report as a read-only projection, without controller API credentials, and invokes `sdo-operator late-findings --incident-id ID`. The command returns logical detector and playbook IDs and writes a bounded pull receipt. The broker checks the worker's typed pull claim against controller-owned telemetry before recording it in closure evidence.

Incident responders never merge directly into the operational branch. The broker creates isolated worktrees, checks path ownership and append-only rules, runs repository and detector validation, and accepts only attributable commits. Two repair-evidence policies are supported. `commit` retains a proposal commit for every response, including an empty attribution commit. `recorded-actions` permits a live-only repair without a proposal commit when the responder returns a structured, successful action receipt; any repository changes are still validated and committed. In both modes the controller commits the authoritative outcome and reflection, and independently owned health detectors must verify recovery. The source deployer separately authors attributable deployment commits during the initial lifecycle. Health detectors remain judge-owned; responders may change responder-owned playbooks and incident detectors after closure.

## Controller/responder interaction

The controller batches persistent findings into an incident request. The request includes the health objective path, architecture path, findings, surfaced playbooks, detector history, an isolated repository worktree, and the selected repair-evidence policy. A responder returns a structured result with diagnosis, applied playbooks, repository changes, and per-action receipts recording the target, timing, success, and reversibility of live mutations. Independent health detectors must clear after the response before closure. If they do not clear within the configured verification timeout, the controller durably records a detector-review-required state and exits with an actionable error instead of leaving the incident open indefinitely.

The controller keeps a baseline of the application namespace's configuration, taken from namespace-scoped informers over Services, workloads, NetworkPolicies, ConfigMaps, Secrets, Roles and RoleBindings. The first healthy evaluation sets it. A later healthy snapshot replaces it only after a two-minute settle period with no unhealthy evaluation, and a maintenance pause resets it. When an incident opens, the request carries `state_changes`: the objects added, removed or modified since that baseline, with field-level before and after values. ConfigMap and Secret data appear only as digests. Kinds the controller cannot list are reported as unobserved. Objects that existed unchanged while the application was healthy never appear. The diff is computed in memory from the informer cache, so it adds no API calls on the dispatch path.

Responder Jobs receive the prober's Service address (`http://sdo-prober.<control-namespace>.svc:8080`) as `SDO_PROBER_URL` when they are dispatched, so a prober pod replaced mid-incident stays reachable. `python3 -m sdo.agents.responder.status_cli` runs one verify burst of the incident's scenarios through the prober. It exits 0 when healthy, 1 when unhealthy and 3 when the prober is unavailable, and only scenarios the steady probe has seen succeed can make it unhealthy. The controller also publishes an `incident_view` in its `sdo-controller-state` ConfigMap while an incident is open (the health-detector findings that still block closure and the current state diff) and passes its location as `SDO_CONTROLLER_STATE`; the status is then also unhealthy while a non-traffic health detector fires, and it lists state changes made after the request was taken. The gate has its own clear hysteresis, separate from closure's: while a blocking finding is clearing, the controller re-evaluates its detector every second for the gate only, and moves it to the view's `clearing_findings` after 3 consecutive clear evaluations spanning at least 2 s. Those re-evaluations never reach the finding tracker or detector history, so closure still waits for the health judge's own clear persistence. Responders must run it before declaring a repair. Each confirmed root cause cites structured live `evidence` (a detector finding, synthetic traffic, a state change or a live observation) and the `explained_detectors` it accounts for. Scripts and manifests go in `static_context`, which is never evidence. After closure, `verify_diagnosis` checks the citations against the request and the post-response detector states. It records a verdict per cause (`confirmed`, `contradicted`, `unverified`, `unattributed` or `no-evidence`) in the outcome record. A cause is `confirmed` only when the responder's own repair backs it: each repair action receipt names the objects it mutated (`resources`), and a successful action that started before the closure's `health_cleared_at` (when the gate detectors began their final clear streak) must have touched the cause's resources. Touching an object in the dispatch-time state diff is enough; otherwise the cause is also refused when a dispatch-diff change was reverted by something other than the responder's repairs. The closure also lists `observed_state_changes`, every object the controller saw differ from the baseline while the incident was open with its first observation, so a `state-change` citation outside the dispatch diff counts only if the controller saw it before the responder's own repair of that object started: a wrong fix cannot cite its own edit (a restart's `restartedAt` stays in the closing view), and a late fault the responder reverted exactly still verifies. When health clears in time but no cause is backed, the cause is `unattributed` and the outcome is `external_recovery`: someone else restored health. A verified-clear closure where the responder made no successful change is `cleared_without_action`. Neither is a mitigation, and the SREGym strict receipt for each is valid and carries `resolution` (`external_recovery` or `cleared_without_sdo_action`) instead of requiring reflection. The verdict does not gate closure. Reflection learns playbooks and incident detectors only from confirmed causes, the broker never reflects on a `partial` or `external_recovery` outcome, and the controller does not surface contradicted or unattributed causes as prior-outcome evidence. Responders label any helper pods or Jobs they create `sdo.dev/responder-helper=true`. When the responder completes, the controller deletes them before evaluating the closure gate and records them in the closure as `cleaned_helpers`. If health clears only after the verification window, the closure carries `detector_review_required_at`; the broker does not credit that recovery to the responder, so the outcome is `partial` and reflection does not learn from it. A one-shot or bounded run exits when detector review is required; a persistent controller logs the review once and keeps observing, because its Job would otherwise restart it into a crash loop that ends detection. A split-namespace install grants this through a narrow pods/jobs delete Role.

Before dispatch, the controller deterministically selects up to three successful prior outcomes using exact finding fingerprints and, secondarily, detector/rule/resource-kind compatibility. Only compact root-cause, repair, playbook, and source-compatibility evidence enters the incident request. The responder treats that evidence as a hypothesis and must confirm, adapt, or reject it against live state; historical actions are never replayed automatically.

After independent health verification, the controller records a versioned per-incident outcome. Reflection receives the closure, current and prior outcomes, and an accepted-commit-bound logical memory snapshot. It starts in a fresh session by default or resumes the responder session when configured with a valid session ID. The agent returns a typed `OperationalArtifactProposal` and a learning decision; it never edits `.sdo/` directly. It may run `sdo-operator memory ls` and `sdo-operator memory check` (the broker's own validator) on its checkout. The Go broker independently validates the typed proposal, actual projected diff, role ownership, provenance, detector tests, and acceptance before publishing and triggering a controller rollout. A justified no-change decision records no new memory artifact. The warm rule uses confirmed prior outcomes and logical playbook IDs; a verified repeated match may skip an unnecessary reflection turn when the broker can prove no new learning is required.

The validator image contains a Docker-layer-cached, trusted Go build-cache seed for the controller SDK and runtime dependencies. Each isolated validation copies that seed into its own ephemeral writable cache before compiling application-owned detectors. This preserves the read-only source, network isolation, and per-run scratch boundary while avoiding repeated cold dependency compilation.

## Controller-installation boundary

The Go `sdo/operator/install/` package installs the controller from the broker-accepted commit. The installer owns controller resources and repository synchronization. The SREGym adapter adds benchmark submission resources, readiness, `production-receipt/v2` evidence, and cleanup without changing controller semantics. Benchmark `recorded-actions` policy admits live-only repairs backed by structured action receipts; broker outcome and reflection acceptance still require independent verification.

By default the controller shares the application namespace. `install.Config.ControlNamespace` (and `sdo-operator host --control-namespace`) instead places the controller Job, repository PVC, credentials, state ConfigMap, Lease, maintenance ConfigMap, and responder and validator Jobs in a separate per-application namespace labelled `sdo.dev/controller-namespace=true`. The application namespace then receives only two namespace-scoped grants bound to that namespace's ServiceAccounts: a read-only observer Role for the controller and the responder's repair Role; no ClusterRole is created. The repair Role is generic namespace-scoped edit on application resources (the shape of Kubernetes' `edit` role, without Secrets or RBAC objects, and with pods/exec, attach and port-forward for parity with the Codex baseline), not a list of particular repairs. Responder pods point kubectl at the incident's application namespace. The controller installer does not rewrite application charts or manifests. A long-running install runs the Go builder supervisor: the Go controller exits after each acknowledged closure (`--restart-after-closure`), the supervisor compiles and records the rollout of any learned detector, and relaunches it in the same pod. The operator-owned `sdo-controller-maintenance` ConfigMap (`state: paused|active`, `generation`) pauses detector evaluation and application observation for planned redeploys while in-flight closure, reflection, and acknowledgement continue; resuming re-lists the application namespace with a fresh informer generation, logs `controller_maintenance` with the generation, and evaluates every detector once. With `reuse_existing`, re-running the installer keeps a running controller whose install fingerprint matches and only re-applies the namespace-scoped grants.

SREGym deletes and recreates the application namespace for every problem (and reconciles away unexpected namespaces and PersistentVolumes). The benchmark's opt-in persistent mode (`persistent_controller = true` under `agent_config.sdo_codex`) therefore installs one controller per application in `<application-namespace>-sdo`, asks the harness through `SREGYM_PRESERVE_NAMESPACE_LABEL` to keep that namespace and its volume, pauses the controller after each incident is verified, and on the next problem re-grants access, resumes with a new generation, and gates fault injection on the first all-clear evaluation after that resume. Per-problem resolution ends at controller-verified health; reflection continues asynchronously. Before the next injection the adapter waits for the previous incident's acknowledgement and supervised relaunch (`reflection_drain`), syncs the controller's repository into the new workspace, and writes the previous problem's strict receipt; pipeline teardown drains the last incident and deletes the controller namespace.

Persistent benchmark experiments may additionally preserve shared cluster infrastructure behind an explicit SREGym-only flag. A durable in-cluster marker gates reuse, and the warm storage/observability installation becomes the reconciliation baseline; application and injected-fault state are still cleaned between attempts.

The installation code provides manifests and orchestration logic; the always-running runtime is `sdo/operator/runtime/` in Go. Unit and Go integration tests validate contracts; successful operation on a particular cluster still depends on cluster access, images, credentials, storage, and the target application's deployment artifacts.

## Shared libraries

- `libs/agent_cli/structured.py` runs every production agent turn through [agentshim](https://github.com/vic-lsh/agentshim). SDO's deployer, health judge, responder, and reflection backends name a provider (Codex or Claude Code) and an access level, and keep their subsystem-owned prompts and Pydantic validation. The access levels map onto each provider's own confinement: `read-only` is Codex's read-only sandbox, or Claude's settings sandbox denying workspace writes plus the Edit/Write tools; `workspace-write` is Codex's workspace-write sandbox (network off) with `sdo-operator memory ls|check` available for read-only memory inspection, or Claude's sandbox with the same commands available. Codex reads that rule only from `$CODEX_HOME/rules`, so each Codex workspace-write turn runs with a private, non-resumable `CODEX_HOME` under `$SDO_CODEX_HOME_ROOT` (default `~/.cache/sdo/codex-homes`, outside the workspace and `/tmp`) holding the rule and a 0600 copy of the user's `auth.json` (or none when `CODEX_API_KEY`/`OPENAI_API_KEY` is set), deleted when the turn ends; `danger-full-access` removes confinement for sessions that operate the cluster. Each turn also returns the shell commands the agent started, which the lifecycle audits for reads outside the application checkout; Codex omits commands its sandbox denied from that stream, which the audit tolerates because denied commands never ran. The worker session directory is retained for seven days after durable acknowledgment, pruned daily, and exported by `runtime-artifacts` under `sdo_runtime/sessions/<incident-hash>/{codex,claude}/`; verified reflection may resume the exact responder session when configured.
- SREGym-specific protocols and runner utilities live under `benchmarks/sregym/`, not `libs/`.

## Supported and excluded scope

Supported production scope is the lifecycle, memory, controller, responder, and Kubernetes runtime described above. SREGym code is supported as benchmark infrastructure.

Excluded from production scope are bounded shell-monitor loops, generated shell health checks, a second deployment lifecycle, standalone Compose fault injection, historical trajectory recorders, and benchmark verdict logic inside production packages.

See [testing-guide.md](testing-guide.md) for validation commands.

Status meanings:

- **Active** — selected by the public production command.
- **Benchmark-only** — lives behind the SREGym adapter and is excluded from production imports.
