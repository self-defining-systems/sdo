# SDO architecture

The deterministic SDK supplies shared snapshot candidate detectors in `sdk/observe` and observed-listener target-port diagnosis and plan proposals in `sdk/routing`. Applications import these helpers instead of copying them into per-app `.sdo/lib/`; app policy, provenance, bindings and app-specific helpers remain in operational memory. This does not share agent-learned code across repositories or change the memory layout. Promotion of the `repair` helper is deferred until XV1 settles its action vocabulary.

This document describes the production boundaries implemented in this repository and the separate SREGym benchmark boundary. It does not treat historical deployment experiments as production features.

## Replay run policy

The single trusted `replay` setting (`on` by default, or `off`) follows the run through
installation (`--replay`), typed `ControllerConfig.replay`, the Go broker and isolated
validator, and worker `SDO_REPLAY`. `sdo-operator memory check --replay` also accepts the
setting explicitly. Candidate memory never changes the broker's policy.

With replay off, the controller captures no corpus snapshots or primitive recordings,
and reflection does not settle positive/negative cases. Capture recording and size
limits therefore cannot block a repair or save. Static and compiled checks skip all
corpus labels, presence and provenance requirements, healthy replay and generated
program replay tests. Compilation, imports, changed-source formatting, ownership,
independent outcomes and successful RunScript receipt provenance remain required.
Hand repairs still need executable mitigation code; receipt-to-case coverage is not
required. Skill projection and tool registration omit replay-specific authoring work.

RunScript uses the exact script digest in the accepted incident outcome. A legacy
receipt without recorded script bytes needs an explicit receipt link in playbook README
front matter (shared helpers use `metadata.yaml`). `script_receipts` maps each digest to
`{incident_id, receipt_id}`, preserving several script revisions without rewriting the
playbook's birth. Legacy `script_origins` with `originating_incident` remains readable. Live planning reads immutable accepted Git blobs and the same receipt
predicate; existing corpus-backed origins also need corroboration by their accepted original
outcome, so unchecked corpus bytes cannot grant execution authority. The logical catalog
excludes corpus contents; optional inert bytes never prevent worker snapshots. Program trust, fresh live
diagnosis, response stages and independent health verification are unchanged.

Corpus remains in the playbook artifact class in the ownership matrix; replay off
changes no repository scope or production/benchmark boundary. Fastloop incident rows
record `replay`; older and baseline rows use null. Offline reflection rows record
`replay_mode`, with disabled replay reported as skipped, never successful.

## End-to-end lifecycle

```text
optional human goal
        |
        v
agent proposal in isolated checkout -> trusted source build/apply/readiness -> broker commit
        |
        v
Go-generated manifest inventory -> broker commit
        |
        v
fresh detection-designer proposal -> bounded detector validation -> broker commit
        |
        v
controller builder/install -> deterministic Go controller -> incident batch
                        -> SDO Prometheus <- annotated application pods / kubelet / OTLP
        |
        v
incident-open coverage -> ordered response stages (deterministic stage first, then the registered responder job when findings remain) -> independent verification -> broker outcome commit
        |
        v
fresh reflection proposal -> broker validation/commit -> controller rollout
```


The architecture reader inventory and per-reader decisions are documented in
[onboarding reader inventory](onboarding-reader-inventory.md).
`sdo-operator host` starts the active production lifecycle; the installed `sdo-operator operate` continues it in the cluster. Go coordinates optional Human goal, Upkeep schema, source-deployment and Go inventory, and HealthJudge bootstrap proposals. The source stage requires a trusted deployment receipt bound to the exact candidate Git tree and immutable running images before publishing; architecture cites the broker-returned accepted source commit. The controller then runs deterministic detectors and independently verifies recovery. At incident open, Go builds finding-bound playbook coverage and runs configured `ResponseStage` implementations. SDO applies a learned playbook automatically when its diagnose matches live and every parameter binds (stage [deterministic, agent]); the agent is told the result and handles what remains; no automatic rollback, no trust gate. The default `deterministic,agent` pipeline first applies accepted playbooks with a fresh Match, one mitigation entry point and complete finding bindings; it waits at most 30 seconds for its own rollouts and retains completed writes. The registered responder receives remaining findings and typed `prior_stages` reports, including receipts, post-apply diagnoses and skip reasons, and chooses further repairs through the menu. `response_stages: [agent]` selects the baseline. A stage never closes an incident; independent controller verification does. Incidents cleared without a responder still receive fresh reflection with stage evidence. Go independently verifies recovery; only the responder decides rollback. Verified program success/failure counts are information, never write authority. Before recording each successful outcome, Go settles learning by confirmed cause. Exact covered repairs and fixed-capture false matches get deterministic corpus cases through normal validation; questions or rejected cases go to in-session reflection. Trust consumes only the persisted covered instances. A full host-to-controller kind smoke passed with live clear detector evaluations; deployment still depends on the target cluster, registry, credentials, and application manifests.

## External incident admission

`Controller.OpenExternalIncident` accepts a stable alert ID, namespace and message
through a transport-neutral API. External-only mode disables detector scheduling,
source-drift admission, health/traffic startup gates, and automatic response stages.
The Kubernetes edge reads a single-slot `sdo-external-incident` ConfigMap with typed
`incident.json`; producers retain the same ID until durable acknowledgment. The
controller uses its existing workspace/dispatch/closure state machine and preserves
external completion identity across ACK/restart. Completion carries no independent
health assertion and currently requires frozen memory: evidence stays private and
never grants learned trust or changes accepted source. Worker snapshots omit the
detector catalog and detector tools report awaiting responder completion.

The benchmark adapter alone sends the generic alert after injection and grades the
cluster with its oracle after responder completion. Fault identity, injection metadata
and oracle answers never enter the production alert or worker request.

## Component boundaries

Core versus deployment plugin-family imports (render, imagesrc, upstream, telemetry) are enforced by `sdo/operator/internal/archcheck`; see [testing guide](testing-guide.md#plugin-boundary-checks-archcheck).

Controller observations compose through `sdk/inputs.Carrier`, a copy-on-write carrier of the optional SDK input sources above the Kubernetes snapshot. Runtime observers add frozen sources to that carrier; they do not wrap and selectively forward detection contexts. Program `ReadView` includes the complete `inputs.Sources` contract, so checked diagnosis, recording, and replay preserve those inputs and the observation clock. An SDK interface inventory test requires every new optional source to join this contract.

The shared runtime mitigation plan builder owns RunScript byte provenance for automatic stages, matched CLI application and follow-ups. It checks actual returned actions against original successful timed receipts in the incident accepted commit; save-time source inspection and offline replay cannot grant execution authority.

Go owns operational decisions and accepted repository state. Python hosts the built-in agent implementations. Registration is implementation neutral: a versioned ProtoJSON `AgentRegistration` advertises an agent ID, capabilities with exact protobuf request/result type URLs, and a launch method. `AgentTask` and `AgentResult` carry typed protobuf `Any` payloads and a proposal workspace. The Go registry rejects unknown IDs, capabilities, and payload types; the generic Kubernetes executor launches a registered worker without knowing its language or model provider. Built-in manifests live in `sdo/agents/registrations/` and are the only source of agent IDs and task types: the controller loads them from a configured directory (`--agent-registration-directory` or `ControllerConfig.agent_registration_directory`, image default `worker_registry.DefaultDirectory`) and resolves tasks by message type URL; third-party workers can use another language if they honor the same contract. Incident, lifecycle, and reflection dispatch use this boundary. Go also owns validation retry: when the broker rejects a reflection or detection-designer proposal with validator diagnostics, Go re-dispatches the task as a new task carrying the typed `MemoryDiagnostic` list and a 1-based `validation_attempt` (`ReflectionRequest`, `HealthJudgeRequest`), at most `broker.MaxValidationRetries` (5) times. Every rejection is recorded durably before the checkout is reset (`BrokerLedger.reflection_rejections` for reflection, a `ProposalRejectionLog` beside the broker workspace for the detection designer), so a restart neither resets nor repeats attempts; once the bound is spent the rejection is terminal (`BrokerLedger.reflection_rejected`, and the detection designer falls back to the whole-deployment retry). Workers only render the diagnostics into the prompt. A lifecycle worker (deploy, architecture, detection designer) only authors a proposal in an isolated checkout, so one whose Job vanished with a stale dispatch receipt is discarded by the registry (`DiscardVanished`, refused for other task types and while a Pod of the Job still runs) and dispatched once more. For the detection designer a repeat is a recorded `worker.job_vanished` attempt on a fresh task, and a rejection log made terminal only by such attempts does not pin later controller starts: the refresh takes the next publication generation (`-gN`). Deploy and architecture failures record feedback text and are bounded by the install attempts. Incident and reflection tasks keep the terminal `JobVanishedError`, which the runtime records as a failed task.

The `.proto` files are the source of truth for messages crossing Go, Python, and worker boundaries. The controller retains SDK types for live scheduling and detector execution, and exports/restores the generated `ControllerState` directly; there is no duplicate persistence struct. Dispatch and closure phases use generated enums. Request, result, and closure projections remain explicit at SDK boundaries. Outcome derivation constructs generated outcome messages directly. The built-in Python workers parse and build the generated messages directly; model-output JSON schemas are generated from the proto descriptors (`sdo/contracts/model_schema.py`) for `IncidentResult` and `ReflectionResult`; the reflection decision file Go loads is that same `ReflectionResult`. The responder and its resumed reflection turn send one session wrapper (`sdo/agents/responder/session_turn.py`): a strict object with nullable `incident_result` and `reflection` branches, plus one shared MCP server set, so the resumed turn keeps the responder's prompt-cache prefix. Each turn fills only its own branch; a wrong or null branch gets one resumed correction before it fails. The controller's persisted state (the runtime-state ConfigMap) and the broker ledger are canonical ProtoJSON of `ControllerState` and `BrokerLedger`; the Go structs in `runtime/protocol.go` carry no JSON tags and convert through `runtime/contract_projection.go`. Closure and reflection decisions use pure generated-state transitions in `runtime/lifecyclecore`. Their private I/O adapters and the default runtime observation clock and development timing environment live in `runtime/internal/lifecycleio`; only the driver persists transitions and executes effects. Failed closures use a content-addressed ConfigMap archive outbox before later effects are authorized, and registered reflection requests are durably frozen outside proposal checkouts. See [the lifecycle specification](lifecycle-state-machine.md) for states, events, invariants and the functional-core extraction plan. The incident view published for Python and benchmark readers is a ProtoJSON `IncidentView`. Canonical ProtoJSON omits empty fields, so readers tolerate absent keys. Reflection consumes generated outcome messages directly. Dynamic finding metadata is the only field in the Go incident projection that needs a JSON value conversion. Conformance tests cover the projections and reject contract drift.

Controllers may share one accepted application checkout while keeping separate proposal, session/corpus and broker-ledger roots. The existing application-root/repository-mount configuration selects that checkout; sharing across hosts requires a shared filesystem that honors the broker's file lock. The broker lock lives in the accepted repository's Git common directory, so separate controller workspaces serialize the full validation and accept transaction. Stale diffs are three-way replayed onto the current accepted head; the complete `validate.Check` and independent compiler validate that merged tree. Text conflicts and merged-tree validation failures return typed `MemoryConflict` provenance through `MemoryDiagnostic.memory_conflict`, including affected paths, accepted commits/incidents and validator errors. Reflection resumes the same provider session in a fresh current accepted checkout and merges both intents; after a conflict, at most three total publication/correction attempts are allowed. Verified deployment-source publication still requires its exact deployed base/tree. Incident IDs must be unique across sharing controllers. Live eval lane mounts, cross-cluster storage and runner orchestration remain benchmark concerns. Controllers on different hosts share memory without a shared filesystem through `ControllerConfig.memory_upstream` (`--memory-upstream-url`, `--memory-upstream-branch`, `--memory-upstream-ssh-dir`; `install.Config.MemoryUpstream*`): each keeps a private accepted checkout and its broker replicates one remote branch (`broker.Upstream`). Every broker operation first syncs (push local history, fast-forward to peers'); a publication pushes its validated commit before the local fast-forward, and a rejected non-fast-forward push re-syncs and repeats the same replay and full check, with jittered backoff for up to three minutes. An unreachable remote never blocks the controller: publications are accepted locally and pushed by the next operation; path-disjoint offline history is joined by a merge commit whose first parent is the remote head, overlapping offline history stays local and is preserved on `<branch>-unmerged-<commit>`. The branch must exist and is never `main`/`master`; the ssh identity is an existing key mounted read-only.

Catalog reads for incident and reflection tasks use `memory.SnapshotAt` with the prepared proposal's accepted base. The Git storage edge projects raw immutable Git blobs without checkout filters or a shared index, so peer publications cannot mix revisions or substitute newer learning into an already frozen task. Ordinary latest-head reads retain their clean-checkout checks.

Native incident and reflection tasks carry an accepted-commit-bound `OperationalMemorySnapshot` with goal and architecture text, logical detector registrations, and playbook IDs/content. Reflection edits final operational-memory files in its isolated checkout and returns decisions and logical playbook IDs. For a successful session-free deterministic-stage incident whose finding coverage is bound to verified accepted-program applications, Go first offers `no_change` to the complete broker check. No worker or model starts when that check accepts and no new evidence requires learning. Resumed sessions retain the worker-owned writer quiescence/handoff. Otherwise, the built-in worker first offers `no_change` to the existing Go memory check; if accepted it returns without a provider call, while a failed or timed-out probe continues through the normal session. Resumed native completion still acquires and releases reflection ownership, permanently preventing a stale responder from reclaiming that session. The Go broker derives the actual diff and calls the same `validate.Check` as the local CLI before publishing. A reflection self-check uses the incident-scoped session transport to run that pipeline on a broker-private frozen candidate, and the broker independently repeats the shared check before publishing. Worker reports carry no publication authority, and attestations never enter operational memory. Clean peer changes are three-way applied and revalidated without another model exploration; colliding edits remain correction work. Accepted program and detector changes activate in the memory host; the controller is never rebuilt for them. During response, playbooks and shared libraries are editable working code. Agent program commands compile changed dependency closures on the controller with its warmed Go cache. An isolated Go program forwards read-only view calls and returns typed plans to the ordinary controller executor, preserving bindings, receipts and independent verification. Program revisions use `working-tree:<source digest>` until publication. Source publication projects only source repairs; working playbook changes remain in the incident checkout and seed the resumed reflection checkout exactly once. Reflection submits those drafts through the complete memory check and broker validator. The detection designer uses the versioned `health-judgment-direct-v1` capability to edit final health detector, traffic and health-objective playbook files directly. It returns metadata and logical detector IDs and rejects retired proposal payloads. Dispatch pins `SDO_ACTOR=health_judge`, `SDO_PHASE=initial`, and the accepted base. The explicit `memory.PrepareHealth` step in `validate.Check` installs generic service-endpoint, workload, wiring, warning-event, node, resource-saturation, runtime-crash and traffic detectors from the final workloads, then the same validation and compile pipeline checks the prepared tree. The broker publishes all prepared files; independent health verification remains separate. The judge can refine health diagnostics after bootstrap while source, goal, outcomes, incident detectors and other playbooks remain protected.

The controller captures the application namespace's detection view at detection (`open@detect`), immediately before the first live repair (`open@pre-apply`), and at verified close (`fixed`) under the private incident session; with no pre-incident healthy reference, the controller binds the `fixed` capture as the incident's healthy sample for detector checks. The `open@detect` snapshot is written before the responder is dispatched; its routing sweep runs in the background and never delays dispatch, and the worker requests a controller-owned pre-apply capture before `sdo act` executes locally. Typed plan application uses the same first-mutation boundary. Pre-apply reads a fresh provider snapshot, preserves detect unchanged, and adds no probes or settle delay; the protected file is reused across repeated commands and restarts. Capture failure records an evidence gap and allows the repair and its receipt to proceed; controller-observed failures retain `pre_apply_capture_gap` across restored responder state, so later commands cannot substitute a repaired snapshot for the missed boundary. For finding Services, Services the snapshot shows as unroutable (no ready selected Pod, or an integer targetPort no selected Pod declares), and up to two ready healthy peers in that priority order, the controller also records real TCP observations at Service ports/targets and at selected Pods’ declared ports and numeric targets, using captured Pod IPs through the read-only memory host. Automatic sampling is bounded to 24 probes per capture, two Pods per Service, four backend ports per Pod, 4 s per probe and six seconds total. Fixed snapshots refresh these reads. Declarations choose candidate probes; they do not prove a listener. Captures retain ConfigMap `data`/`binaryData` key names with empty values and
`sdo.dev/configmap-values-redacted: "true"`; live detector reads retain their
original values. Previously accepted immutable corpus cases are not rewritten.
Captures omit Kubernetes write metadata and sensitive environment values. Reflection saves useful repair steps, including receipt-linked RunScript bash, and README orchestration even with partial coverage. Verified README-only guidance is allowed and never auto-applied. Replay fixtures are optional: missing evidence, open NoMatch, persistent post-plan Match and failed assertions are informational, never publication gates. Compilation, imports, changed-source formatting, ownership, hygiene and receipt provenance remain required. Accepted corpus cases stay immutable. Independent live verification owns recovery.


RunScript is a first-class learnable mitigation alongside typed actions. Mitigate
returns inline bash and relation-derived Values resolved into process environment.
A fixed tool image executes an application-local Job with `backoffLimit: 0` under
`sdo-script`, which holds the same cluster grant as every SDO identity. The installer accepts `--script-image` for the
slim `script-tools` build target; existing installations reuse the cached trusted
controller image. Script execution defaults to 60 seconds, bounded by five minutes
and the remaining incident budget, including a short evidence-publication reserve.
Scripts and each retained output stream are bounded at 64 KiB.

An application-local private ConfigMap reserves the application before Job creation
and records the Job UID. A restart joins that Job or recovers its result; an
uncertain missing/replaced Job never permits another invocation. The native runner
routes kubectl through the existing Kubernetes proxy, checkpoints first-write
preimages before forwarding and records settled postimages, receipts and explicit
capture gaps. Object images use private chunked ConfigMaps so a large object or repair batch
cannot exhaust the bounded result envelope. Raw output/preimages stay at that runtime storage edge; durable
outcomes retain references, digest, exit code and input provenance. Arbitrary
external effects remain opaque. Undo is explicit only; script undo from captured
preimages is follow-up work.

Script corpus labels link the authored SHA-256 digest to the original successful
timed repair receipt. The memory gate accepts `observed-transition`: open Diagnose
must Match, fixed Diagnose must return NoMatch and bindings/inputs must validate.
It never supplies fixed captures to the action simulator or claims the rewritten
script ran. Live reuse goes through the ordinary apply→Diagnose and targeted
finding-clearance loop, while global health continues to own closure. Final
settlement records `final_verification_basis: observed-transition` after a fresh
bound diagnosis and scoped health sample; it never claims exact typed-effect
equivalence for a script. The same basis settles every action kind whose effect
lies outside Kubernetes objects (`planwire.NonObjectEffect`: exec, ensure, database
user, Job, script), after each such action's own recorded success.

generated schema checks their kinds, and neither the responder nor the
controller re-checks or retries an evidence source.

Go module `benchmarks/sregym/protocol/native_receipt_go`. Its

contracts only; production Go packages do not import the benchmark module.

to `protocol/submission_go`. `benchmark_submission.proto` defines those facts,
phases, terminal-stage spellings, and the Go guard's typed decisions. The guard

field types and rejects undefined lifecycle enums. Source-mode operator launches
use a cached build, so observation polling does not repeatedly use `go run`.

## Mitigation menu

The menu is a convenience over direct commands. `sdo menu` lists accepted Mitigator programs with their
declared object and value parameters and registered raw plan actions as generic one-action plans.
`sdo mitigate OPTION [--NAME VALUE ...] [--rounds N]` runs the selected option through the ordinary
`PlanExecutor` under the controller's existing RBAC and always-on executor checks. The option catalog
comes from program and action registries, so adding an action requires no menu-specific execution case.
The menu adds no selection ledger, fences, quiescence, provenance, health-reader or credential-delta
preconditions. Direct commands and recorded `act` remain available in the same responder session.

Current source-absent `drift.unexplained` findings also expose a `remove-unexplained` option bound to the exact UID/resourceVersion. At the API delete boundary Go rechecks the current accepted-source inventory, onboarding acknowledgements, SDO ownership and control namespace. The controller executes and audits the conditional delete; the installer assigns discovered non-secret get/delete grants to the non-workload user `sdo-unexplained-removal:<control-namespace>`. Only the checked callback uses a separate transport impersonating that identity; generic menu/program actions retain the controller identity and its original grants. Controller impersonation is restricted to that exact user; no removal ServiceAccount or token is created. Generic object, raw API and exec clients, including diagnosis read views and observations, reject control-namespace access so plans cannot create controller-identity workloads or acquire controller credentials. Added removal authority is disabled when application and control namespaces coincide. Worker RBAC is unchanged. Cluster bindings require exclusively application ServiceAccount subjects. Cluster roles require every referencing binding to be removable and exclude bootstrap, built-in, system and exported aggregate roles. A separate complete RBAC ownership graph includes foreign RoleBindings; live ownership reads repeat the check before conditional deletion. Shared authorization receives a `shared_ownership` removal blocker in the menu and is never offered for removal. Direct command receipts retain only the explicit patch/delete targets, and deletion receipts require absence readback, and failed actions retain typed reasons. Source-absent inventory objects are drift information: they are listed in `drift[]` and recorded on the outcome, never held against verification or closure, so they cannot stop a response early. The all-denied stop remains `authorization_denied_no_progress`. The menu lists typed `unexplained_removal_blockers` for current findings that cannot be offered. Typed launch initializes the ordinary exec/dynamic transports even after constructing its own Kubernetes client; only explicitly caller-injected clients skip ambient credential setup. Go persists its terminal findings; health windows and pending rollouts retain the verification grace. Raw DELETE resolves its named whole-object path through discovery, rejects conflicting references, and requires confirmed absence; pending or unavailable readback reports `delete_not_confirmed`. Tool output separates five mitigation rounds from the provider continuation budget; final response-loop accounting counts provider executions. Supplied Kubernetes clients retain authenticated generic API transport and unsupported typed object kinds resolve through discovery. Unavailable API/exec actions are omitted from the menu.

Versioned generated menu/report contracts carry session, attempt, round and action identities.
The tool response includes parameter schemas, what ran, per-action results, each value's provenance,
and any error. Failed and successful reports return to the same responder session so it can choose
another option or fix the problem directly. The incident allowance is at most five rounds, shared
across options and ordinary plan batches; a smaller configured allowance remains effective.
The automatic response stage sends all its matched plans in one apply with one rollout wait, inside a
fixed 45 s stage budget (`DefaultStageBudget`); that apply is numbered separately and never spends the
agent's rounds. Matches the stage could not apply or verify in time reach the agent in `prior_stages`
with skip reason `stage_budget`.
The stage runs again, on the responder's own loop, when a finding that a learned playbook explains
activates after dispatch (`attachLearnedActivation`, at most eight passes, each within the same budget).
The finding joins the open incident, a pass redoes attempts that were only skipped and never repeats one
that wrote, and the one `deterministic` report in `prior_stages` is updated in place. The responder reads
the new attempts once, as `prior_stages` in its next tool reply.
The stage reads the accepted application map. A plan that restarts, deletes, rolls back, scales down,
reconciles, patches, applies or sends a write request to a workload marked `holds_data`, or its Pods or
ReplicaSets, is skipped with reason `holds_data` and the finding goes to the responder. At closure, a
`holds_data` workload with a Pod created since the incident opened (or a restarted container) and only
volumes that die with the Pod makes the outcome `unconfirmed` (`DATA_MAY_BE_LOST`).
Evidence for source-reconcile learning: every resource a write names, at each write boundary and at
detect, gets one `DiffAgainstSource` recording in the incident capture (`recordSourceComparisons`); an
object with no acceptance record keeps its declared-field result and the typed reason
`acceptance_record_unavailable`.
Private session/checkpoint messages retain provider identity for presentation, without mutation authority.
Session presentation, reports, repair receipts and counters survive through the existing tool-state
snapshot. There is no selection journal, report outbox or menu-specific mutation fence. In-process
applications retain preimages for explicit `rollback`; preimages are never restored or replayed.
A fully applied option that fails verification remains in place. Its report identifies the application,
states whether changes remain and exposes the error; only a partial write failure triggers the
ordinary executor's automatic compensation.

Menu action receipts enter ordinary incident repair evidence. A terminal menu success is not independent
broker closure or positive program trust credit. Controller health verification, broker ACK and the
benchmark adapter's strict receipt remain separate evidence. See the
[analysis reference](../.agents/skills/analyze-experiment/references/mitigation-menu.md).

## Benchmark fault and result boundary

`benchmarks/sregym/faults/description.py` owns the versioned
`sdo.sregym-fault-description/v1` metadata contract. Its harness subprocess
resolves registered singles, catalog composites (excluding decoys), and generated
co-located composites without cluster access. Descriptions preserve declared
indices, actual injection order, class/key, parameters, probe availability, and
required repair/snapshot scope. The runner and both fastloop selection paths
validate this scope before deployment. Namespace labels/PSA, ResourceQuotas,
admission webhooks, and unreviewed fault classes fail this check; production
Roles and informers remain application scoped.

Fastloop records `fault_descriptions.json` alongside incident results. Composite
analysis reads that recorded catalog, avoiding a second hand-maintained fault
map or dependence on the analyst's current harness checkout. Unsupported probes
use the official aggregate oracle and record `tracking_supported=false` with no
per-fault resolution times. `--require-fault-tracking` rejects such runs before
deployment. Hidden identities, injection details and oracle answers stay in this
benchmark boundary and never enter production tasks or operational memory.

The sdo3 v2 worker and deferred HTTP gate expose explicit injection validity.
Invalid injections stop before response/receipt polling; the persistent adapter
pauses maintenance and records benchmark infrastructure evidence. Fastloop
performs full cleanup, records an infrastructure row without learning credit,
and excludes it from incident summaries. Full recovery errors stop the warm
stream, including continue-on-error runs. Component addressing flattens every
worker-returned index; official aggregate oracles retain collateral/traffic policy.

The pipeline accepts terminal infrastructure rows in both per-problem and
`run_<attempt>` layouts, records their state as `invalid_infra`, and preserves
resume and workspace chaining. Such rows require no agent verdicts or strict
receipts; invalid injections still require injection evidence. Analysis checks
the top-level `infra_error` before token, submission and receipt requirements,
excludes these rows from agent scores, and preserves independently graded
aggregate failures with only per-fault infrastructure details. Composite metrics
retain fault counts, injection validity and per-fault details beside existing
aggregate success and timing. The harness owns selection and validation of its
immutable checked agent image; the adapter no longer probes an obsolete tag.

### Scoped observation

The installer owns a versioned `ObservationScope` ceiling, separate from memory and ambient Kubernetes permissions. `host --observation-ceiling-json` accepts trusted JSON with `version: 1` and explicit `targets` (`api_version`, `kind`, `namespace`, or a cluster object's `name`). The installer validates the ceiling, provisions it as an explicit controller/operate environment value, includes it in the install fingerprint, and grants read access only to the runtime controller and trusted Go bootstrap observer. Foreign namespace Roles permit Deployment, Service and Endpoints reads; admission webhook ClusterRoles permit GET only for individual declared names. These grants add neither foreign Secret reads nor responder repair privileges. A missing ceiling permits no additional observation. Reinstallation changes policy; accepted memory cannot change it.

Architecture front matter may declare `observation_scope` version 1 with `namespaces: [{name, kinds: [{api_version, kind}]}]` and `cluster_kinds: [{api_version, kind, names: [...]}]`. Namespace kinds are limited to `apps/v1 Deployment`, `v1 Service` and `v1 Endpoints`; cluster kinds are the two `admissionregistration.k8s.io/v1` webhook configurations, by explicit name. Unknown versions/fields, wildcards, duplicate targets and more than 32 targets are rejected. Broker validation checks declarations against its own immutable ceiling and checks detector watches against the architecture. Proposal self-checks receive an advisory copy in private Git metadata; forged copies and proposal environment values never override broker authority. Existing architecture ownership still excludes responder source and reflection proposals.

The runtime reads the architecture from an immutable accepted Git revision. Its generation binds that revision and the canonical scope/ceiling identities. Legacy SDK accessors remain application local. The optional `ScopedObservationSource` provides copied, sorted, credential-free scoped objects and per-target availability. Scoped reads use fresh, bounded LISTs and named webhook GETs at snapshot time; their cache retains projected prior objects only for comparison, and emits qualified scheduler events. Each target has a two-second deadline, a 500-object cap and a shared two-MiB projected-output ceiling; failed targets retry with per-target exponential backoff capped at thirty seconds. This polling path needs no foreign watch or cluster-wide webhook list privilege. Application-local informers are unchanged.

Successful empty lists and named GET NotFound mean observed absence. Authorization failures are `forbidden`, missing APIs `unsupported`, and other failures/caps `unavailable`. Error bodies are omitted. Failed targets return accessor errors and declared detector dependencies remain Unknown/error, so they cannot clear findings. Healthy baseline promotion requires complete scoped coverage, preserves the previous state during gaps, and compares only observed targets after a fresh read. A new controller/scope generation establishes its own baseline without synthetic object changes.

Foreign Deployments expose replica counts, selector/template labels and container name/image/ports/resources; environment values and references, commands/arguments, volumes, probes, annotations and arbitrary status messages are excluded. Foreign Services retain routing identity, selector and ports. Endpoints retain sorted ready/not-ready addresses and ports without target references. Webhooks retain rules, selectors, policies, timeouts, service identity and URL origin; URL userinfo, path, query and fragment are removed, service paths and match expressions are omitted, and CA bytes become a SHA-256 marker. Bounded v1 limitation: changes only to webhook service/URL paths or match conditions are invisible to watch comparison, source drift and replay. Those fields remain excluded from the credential-safe projection; observed equality is limited to the retained fields. All new paths share these projections before SDK access, drift, baseline or capture publication. Read-only source comparisons normalize the observable Kubernetes defaults without foreign dry-run writes. Scoped observations add no Secret access. Application-local ConfigMap values remain omitted from captures only.

Captures persist `scoped_observation` version 1 with accepted generation, scope, target statuses and projected objects. JSON replay exposes the same optional interface without network access. State changes carry API version and namespace in runtime and protobuf projections; cluster namespace remains empty. Reviewed webhook configuration changes, including source-absent creates/deletes, require successful accepted-source lookup. Read-only qualified lookup preserves foreign/cluster identities from the accepted source selection; it grants no foreign image fallback or apply authority. Initial reads are suppressed. Endpoint turnover wakes dependencies and supplies baseline evidence without opening configuration drift incidents. This increment adds no metrics, collector or resource-health detector.

### Synthetic traffic

The detection designer writes Go generators (`.sdo/diagnostics/traffic/generators/`, a package exporting `Scenarios() traffic.Catalog`) and workload profiles (`traffic/workloads/<name>.yaml`). A scenario is a user journey: steps whose endpoints build requests from a seeded rng and per-iteration state and check responses, the Services on its request path (from `.sdo/arch.md`, for localization), a side-effect class (read, idempotent write, or write with cleanup steps), a synthetic-data marker for writes, and the fault classes it must detect. A workload is data: purpose (`health-probe` runs continuously and feeds a traffic health detector; `verify-burst` and `journey` run on demand for a bounded time), scenarios and weights, arrival pattern and rate, timeouts, and per-scenario SLOs. Its schema is defined once in `sdo/contracts/proto/sdodev/contracts/v1alpha1/traffic.proto` and code-generated for both sides; protovalidate CEL carries the invariants that do not need a Go-duration parse (duration bounds stay host code).

The `traffic.Engine` owns scheduling, arrival, rate, in-flight and time caps, latency measurement, and seeding: iteration *n* of a workload always builds the same requests, so any failing probe replays exactly. It refuses unsafe requests (writes from read scenarios, writes without the marker) without sending them. The builder compiles generators only into the accepted memory host (with workloads embedded), never into the controller; generated tests prove that every scenario fails against simulated unreachable and 5xx targets plus its declared classes, that workloads name provided scenarios, and that traffic detectors consume health-probe workloads, and a static guard rejects generator imports that reach the network, filesystem, or cluster and package-level clock or rng calls.

The detector SDK and runtime snapshot component observes namespaced StatefulSets, DaemonSets, Jobs, CronJobs, PVCs, ServiceAccounts, HPAs, PDBs and Ingresses through change-driven informers, plus cluster-scoped read-only Nodes. Secrets are transformed before informer storage into identity, type, labels and sorted data keys; values and annotations cannot enter detector snapshots or captures. Program read views inherit these accessors.

The memory host owns read-only routing probes even without traffic workloads.
`--synthetic-traffic=false` disables background workloads while retaining primitive
probes. Manager restores scheduler intent on host recovery and swaps immutable
artifacts across accepted revisions without replacing the controller. Missing
routing capability is recorded as a typed unavailable note, never a successful
connection. No standalone prober binary, publication cache, pod, Service or policy
is installed.

Declared `links` TrafficWorkloads (`purpose: link-probe`) probe source-grounded Service dependency edges from the host-owned prober. Each sample uses one fresh connection and one shared connection/reply timeout, on the unchanged default 1 s interval. `protocol` defaults to `tcp`; `http` GETs `http.path` (default `/`) and accepts the inclusive `http.statusMin`..`http.statusMax` range (default 100..499). `grpc` checks `grpc.health.v1.Health/Check` for service "" over plaintext HTTP/2, with optional `grpc.tls` using system trust and hostname verification; SERVING and valid RPC error statuses (including UNIMPLEMENTED and UNAUTHENTICATED) prove gRPC reachability; negative health results, transport failures and timeouts fail. Store protocols are credential-free handshakes: `redis` PING (PONG or auth-required), `memcached` version, `mongodb` OP_MSG hello on admin (ok=1 or auth-required), `postgres` SSLRequest (S/N), and `mysql` protocol-10 greeting or server error. These establish protocol reachability, not authenticated query success. Wrong replies fail rather than qualifying the edge. Samples record latency, status, a bounded 256-byte excerpt/error and a failure class (`refused`, `timeout`, `reset`, `protocol_error`, `not_serving`, or `transport_error`). The link detector includes protocol and recent sample details in finding evidence and metadata. It retains the existing qualification and consecutive-failure hysteresis: a link must first succeed, then fail repeatedly before opening an incident. TCP-only routing probes and service-reachability remain separate APIs.


The native `--healthy-baseline` opt-in also enables a trusted pre-dispatch reachability baseline gate. With no restored incident or pending closure, it collects fresh dial rounds while independently evaluating every other health detector, including the authored objective and traffic. Only measured failing targets in that independently healthy state become exclusions. The record is per-cluster controller state, never operational memory: the gate writes it atomically to `<repository mount>/.sdo-runtime/reachability-baseline.json` on the lane-private repository volume and the running controller judges against it in place, without a broker commit, detector-bundle adoption or restart. Every cluster measures its own record at startup and resume against the accepted head it runs, so lanes sharing one accepted tree keep that tree byte-identical. A measurement that cannot run or pass (goal firing, application still rolling, a read failed) never stops the controller: the baseline is unavailable, never-served targets report Unknown in the detector's reason instead of findings (targets seen serving still fire, and the detector stays confirmed so closure never waits on it), and the controller measures again once the goal is healthy and no incident is open. The immutable generic Go policy remains unchanged. Empty records avoid repeated capture; restarts consume the cluster's own record; deployment-time `--evaluate-once` runs before any measurement and judges without one. The legacy `.sdo/diagnostics/detectors/health/service-reachability/baseline.json` written before this move is never read, the shared check's generic health preparation deletes it, and the validator rule `memory.cluster-local` rejects writing it or any changed memory data file carrying a cluster-local field (object UID, resourceVersion, creationTimestamp, allocated cluster/pod/host IPs, `capturedAt`/`observedAt`). Each exclusion binds the accepted application-source hash and objective digest to the Service identity/spec, selected backend container configuration, referenced ConfigMaps and selecting network policy. Changed source, objective, targetPort, selector or backend/config/policy invalidates the exclusion; ordinary incidents and previously unobserved targets retain normal detection, including targets with no successful dial. Findings expose invalidation through per-port `baseline_status`. Secret resources are never read by this gate. No agent can author exclusions: only the controller's gate writes the record.


### Metrics

Detectors may consume high-level metrics from a Prometheus-compatible API, an optional input that follows the synthetic-traffic precedent. A detector declares `metrics.Query{ID, Source, Expr, Range, Step}` through `metrics.Consumer` (and `metrics.AlertConsumer` for alerts) and reads frozen results with `metrics.ResultFrom`/`AlertsFrom`; it never does I/O. With bound sources (the operator environment's, plus the accepted revision's; credentials read on every request), the runtime's `MetricsObserver` evaluates each declared query once per evaluation cycle at one timestamp, concurrently, with a per-query timeout (5 s) and bounds on query count (32), series and alerts, and freezes the results into that cycle's snapshot (`MetricsSnapshotProvider`). A cycle whose detectors read no metrics sends no request. `runtime` sees only the `MetricsAPI` interface, backed by a `telemetry.Resolver` over the bound sources, opened from the `telemetry.Registry` the entry point wires (the sources come from `--telemetry-environment` and the accepted revision's `sources.yaml`, rebuilt at each memory swap; evaluate-once and the accepted-detector probe get the same bindings from the memory host built from `--app-root`). `Query.Source` names the source (empty selects the default per the resolver rule, and the read key includes it); `Expr` is the source's dialect, passed through unparsed; alerts merge every alert-capable source and each `Alert.Source` is set; errors read `telemetry source "<id>" ...` and name the bound sources; each source gets at most 8 concurrent requests; Prometheus wire handling lives in `telemetry/prometheus/`.

"Metrics source unavailable" is a distinct state. A timeout, 5xx, malformed response, oversized result or no bound source becomes a per-query (or alerts) `Error`, which detectors return as a detector error: it never counts as healthy, so it blocks closure, and never as firing, so it opens no incident. `evaluate-once` requires a bound source when a detector consumes metrics. `metrics.NewThresholdDetector` compares each series' (last, min, max or average) value with a threshold and maps labels (defaults `namespace`, `deployment`, `pod`, `service`) to the primary Kubernetes resource; findings carry the query, value, threshold and labels as evidence, which incident requests retain. `metrics.NewAlertsDetector` reports one finding per firing alert whose namespace label names the application namespace; pending alerts are ignored and alerts without the label are counted in finding metadata. Detectors declare the `metrics.Watch` pseudo-kind and run on their interval; the runtime does not emit it. Captured corpus snapshots do not include metrics, so metric detectors are checked with `sdktest.Snapshot.Metrics`/`Alerts` fixtures rather than corpus replay.

New installs apply the telemetry profile `prometheus-default` unless `--telemetry-profile` says otherwise. The profile (`telemetry.Profile`; built-ins `prometheus-default` and `none`, a YAML or JSON file, or an inline JSON document) names the mode, the backend recipes the installer applies, the cluster reads it grants and the sources it provides; repeatable `--telemetry-source ID=URL` adds external Prometheus-compatible metrics sources (the first becomes the default when the profile has none). `--no-observability-stack`, `--metrics-url` and `--metrics-publish-url` are removed. The `prometheus` recipe (`telemetry/prometheus/recipe`, typed objects behind `telemetry.BackendRecipe`, injected by `operatorcli/catalog/telemetrysources`; the installer imports only the interface) is the SDO-owned single-replica Prometheus (pinned upstream image, emptyDir, six-hour and 1 GB retention bounds) in the control namespace; a golden over the plan objects (`install/testdata/observability_*.golden.json`) pins its bytes. It scrapes application pods annotated `prometheus.io/scrape: "true"`, `prometheus.io/port` and optional `prometheus.io/path` (default `/metrics`), plus kubelet/cAdvisor on nodes hosting running application pods via authenticated API-server proxies. cAdvisor samples are restricted to the application namespace. Its ClusterRole allows pod/node discovery and node proxy reads. The internal Service also accepts OTLP HTTP metric pushes at `/api/v1/otlp/v1/metrics`; storage is ephemeral. No public ingress is installed. The installer writes the controller's telemetry environment (derived from the profile: mode, provided sources, publishing base) into the `sdo-telemetry-environment` ConfigMap mounted at `/sdo/telemetry` (`--telemetry-environment`); `prometheus-default` provides the stack as the default source `prom`. The operate Job receives the resolved profile as an inline JSON `--telemetry-profile`. The controller has no `--metrics-url`, `--metrics-publish-url` or `--metrics-token-file`. The lifecycle coordinator runs a telemetry apply phase on the staged health candidate, after the live deployment checks and before the independent detector evaluation (`Coordinator.TelemetryApply`, `telemetryapply.Applier`): the designer's backends are deployed and ready before detectors are evaluated, the accepted operability report records what was applied (`O3.telemetry` pass), and a denied or not-ready backend fails closed as a typed designer correction (`operability.O3.telemetry` diagnostic naming `backends.yaml`). Every path that verifies a designer candidate applies first, from the controller's environment document (`deploywire.TelemetryApplier`, via `broker.ControllerTelemetry`): the health refresh coordinator through `Coordinator.TelemetryApply`, the upstream advance and source repair through `lifecycle.TelemetryAppliedVerifier` (a typed denial there is a pending verdict naming the reason and file, not a source fault); `TestEveryVerifyCandidatePathAppliesTelemetry` enumerates the call sites. A backend that sets `params` is denied (`denied`: no recipe takes parameters) rather than silently ignored. The controller re-applies the environment's binding policy (`telemetry.Policy.CheckBinding`, the check the broker runs at publication) when it opens designer bindings; the environment document carries the namespace, host and credential grants for it. Every controller-launched agent (refresh judge, responders, reflection) receives the broker's telemetry policy as `SDO_TELEMETRY_POLICY` (`broker.ControllerPolicyEnvironment`, via `AgentWorkerEnvironment`), so its `memory check` runs under the policy the broker enforces. A typed `TelemetryContext` (mode, sources with adapter dialect, endpoint and publish block, granted cluster capabilities, the backend recipes offered, and the namespaces, hosts and credentials a binding endpoint may name) rides on the judge, incident and reflection tasks; Go builds it from the environment plus the accepted revision's bindings (`telemetrycontext.Build`, rebuilt on every memory swap), the judge may bind sources only while the mode is open, responders read it read-only, and a query endpoint alone implies no publishing support. The controller receives the provided sources through the environment document (`ControllerConfig.telemetry_environment_file`) and the broker's telemetry policy, derived from the same profile, provides the same bindings; the broker and the judge's `memory check` install the generic `metrics-alerts` health detector through `memory.PrepareHealthWith(HealthOptions{AlertSources})` only when an effective source (provided plus designer-bound, `validate.EffectiveTelemetrySources`) has the alerts capability, and remove the Go-installed package otherwise (a tree from an environment that served alerts keeps no detector that could only read an unbound source). The generated compile test resolves every detector metrics query against those sources (`telemetry.unbound`, `telemetry.kind`). Threshold detectors are application-specific and judge-authored.

External incident admission belongs to production runtime; generic alert delivery,
oracle grading and ablation selection remain in `benchmarks/sregym/`. Neither may
publish learned memory in frozen mode.

There is no rendered deployment lock. `AcceptedManifest(s)`, adoption, drift, `ReconcileFromSource` and closure render accepted source directly from Git, like `kubectl diff` and `kubectl apply`, and desired state also includes the accepted deployment's image pins: `rendered.Source.Pins` (a `PinProvider`) replaces each pinned container's image with the digest the deployer applied, for the effective tree the pins were recorded for, and for a later accepted tree (a responder patch, values or overlay edit, any source commit that has no deployment of its own) per container while nothing that image was built from changed: the declared source image and the Git objects at its recorded build context and Dockerfile paths are compared between the deployed and the current effective tree, unknown inputs inherit nothing, and a context of `.` covers the whole tree. A container whose image inputs changed reads its source image until a deployment builds it and records new pins. The logical outcome contract is `OutcomeRecord` in `sdo/contracts/proto/sdodev/contracts/v1alpha1/outcome.proto`. The controller derives it, the broker alone receives `memory.Writer`, and `memory.Reader` exposes `Get` and `List` by incident ID. Reflection receives the accepted record and prior records as typed protobuf fields. The Go JSON storage adapter alone maps an incident ID to `.sdo/outcomes/<sha256(incident_id)>.json`, and stores the versioned document. An unreadable or incompatible document fails the read; there is one operational-memory schema. Consumers never infer physical filenames. Closure phase timestamps, reflection skip reasons, and typed learning failures are kept in the durable broker incident ledger because the outcome document is committed before reflection and is immutable. The source-deployment receipt lives outside `.sdo/` in its own durable ledger bound to an accepted commit; it is information only.

`OutcomeRecord.classification` in `outcome.proto` defines four outcomes, shared by generated Python readers and parity-checked Go constants: `failed` for responder failure or unverified health, `cleared_without_action` for verified health without an accepted source repair or successful repair action, `unconfirmed` when a completed responder has no actionable findings but verification remains incomplete at its frozen bound (`ControllerState.verification_deadline_at`), or a verified closure whose closure-time recheck never saw a complete detector observation window, or whose observer stayed unavailable, within its bound (the detectors' clearing horizon plus two cadences; `IncidentClosure.unconfirmed_reason` is `OBSERVATION_INCOMPLETE` or `OBSERVER_UNAVAILABLE`), and `success` otherwise. The recheck has a typed verdict: an incomplete window or an unavailable observer (timeout, API 5xx, unsynced) waits; a denied observer (RBAC, undeclared or unsupported dependency) fails the closure with `CLOSURE_FAILURE_REASON_OBSERVER_DENIED`; only an active finding, unexplained inventory, unrestored source fields or a detector missing from the adopted policy supersede it. Completed responses return to the controller rather than polling incomplete observations. The existing continuation path offers one resumed turn with typed `verification_blockers` (detector IDs and reasons); unconfirmed continuation and restart preserve the first verification bound and original response budget. The live controller owns the harvested result through closure, including in maintenance; it does not retire it as `OwnerLost`. Unconfirmed outcomes retain named pending evaluations in detector history and commit through the normal receipt path. They are neither success nor failure evidence; reflection still runs on them. Successful outcomes are eligible for reflection and prior-outcome recall. Strict receipts accept success and clearing without action, retaining health, broker commit, incident identity, reflection and rollout checks. Diagnosis citations are recorded claims; neither Go derivation nor receipts independently verify them. Program trust still requires successful outcomes and controller-recorded, revision-bound applications and post-repair NoMatch evidence, including equivalent repairs recorded through `sdo act`.

`sdo/operator/memory/layout` is the only Go package that knows these physical paths: it owns the path constants and builders, `Classify(path)` (kind, ID, ok), the per-kind parsers and typed `Tree`, and the single detector manifest type. Each detector carries its own `manifest.yaml` at `.sdo/diagnostics/detectors/<health|incidents>/<id>/manifest.yaml`; the directory name is the detector ID. Schema version 3 stores playbook references as logical IDs; schema version 4 adds `.sdo/deployment/` and retires `.sdo/rendered/`; schema version 5 adds the optional telemetry binding files under `.sdo/diagnostics/telemetry/`, which the controller reads from the accepted revision. Both migrations only stamp the version. Repositories with any other schema version fail before artifacts are read, with an error naming the found and required versions. The registered `layout.Migrate` chain plans version 1→2→3→4→5 upgrades before writing. Startup Upkeep and `memory migrate` both use `Coordinator.MigrateMemory` and the commit broker; readers still reject noncurrent schemas. Fresh onboarding uses the same schema writer.

`sdo/operator/memory/validate` is the one validator for `.sdo/`. `validate.Validate(ctx, Request{Root, Base, Actor, Phase, Layers})` returns `[]Diagnostic{Rule, Path, Line, Message, Hint}`; validation failures are diagnostics, and the error result is reserved for infrastructure failures (unreadable files, a missing toolchain, a bad request). Acceptance always calls `Check` with all four layers; `Validate` exposes individual layers to internal tooling and tests:

- **Structural**: every `.sdo/` path classifies through `layout.Classify`; no symlinks, secret-bearing names, or files over 256 KiB (corpus files have a separate 8 MiB cap); YAML, front matter, manifests, and Go syntax parse; `schema-version` is current. Changed source files outside `.sdo/` are syntax-checked too.
- **Semantic**: ID patterns, unique detector IDs, `possiblePlaybooks` that resolve, playbook front matter, a playbook index equal to the one Go generates from the active playbooks, scripts that are executable, syntactically valid, and named by their playbook, no physical `.sdo/` paths in the architecture, playbook index, playbooks, scripts, or detector Go source, and Go-written architecture inventory. Completeness (architecture, at least one playbook and detector) is required except in the bootstrap stages before the detection designer.

The policy is one declarative table of kind by actor by phase (`grants` in `ownership.go`) plus diff rules for detector provenance, protected detector classes, schema initialization and Go-owned architecture inventory. The broker no longer has its own path-prefix checks.
- **Compile**: authored source and tests compile against the SDK, pass `go vet`, and retain static registration checks. Test and replay outcomes are informational, including unavailable observations and failure to change diagnosis. The broker uses a bounded child process of the running controller; agent self-checks use the same runner body locally.

The broker's `checkCandidate` calls `validate.Check` on its staged clone. That function runs structural, semantic and ownership checks, then the configured compile runner. The broker supplies its subprocess runner, whose body is `validate.CompileCandidate`; the CLI uses that body locally.

### Detector firing telemetry

The controller records, per finding, whether and when each detector fired. The runtime appends `activated`, `cleared`, `not_persisted` (flagged but gone before the detector's firing threshold) and `batched` (the activated finding joined a dispatched incident) records to a JSONL stream, `detector-firings.jsonl`, in the controller's durable runtime area on the repository PVC (`/workspace/.sdo-runtime/telemetry/`, `--firing-telemetry-path`, default on in job mode). It is operational telemetry, not operational memory: it is outside `.sdo/`, changes none of the six artifact classes or their ownership, carries no benchmark labels or verdicts, and is derived only from the controller's deterministic finding state. Each record has the detector id, class, owner, rule id, fingerprint, severity, parameter bindings, surfaced playbooks, firing/clear counts against the persistence policy, the evaluation iteration, the open incident id (empty if none), and `dispatch_relation`: `before_dispatch` (part of the dispatched batch), `after_dispatch` (activated while the responder was in flight) or `no_incident`. Because the batcher debounces, an activation usually records `no_incident` and a later `batched` record settles `before_dispatch`.

Event ids are a hash of the detector, fingerprint, event kind and a per-finding transition counter kept in the durable controller state, so a replay after a crash between emitting and persisting reproduces the same ids and the sink drops the duplicates; an ordinary restart restores the counters and emits nothing. The file is bounded (4 MiB, rotated once to `.1`, so at most 8 MiB), a torn last line is repaired on open, and a stream left over from an earlier controller lifecycle is archived as `.prev` when no state is restored. Sink failures are reported and never stop the evaluation loop.

The controller also keeps a compact timeline in its state and puts it in the incident closure as `detector_timeline` (per finding: `first_activated_at`, `last_seen_at`, `cleared_at`, `relation`, bindings, `surfaced_playbooks`) with three derived booleans: `incident_detector_fired_before_dispatch`, `incident_detector_fired_after_dispatch`, and `no_incident_detector_fired` (only health detectors fired). `IncidentClosure` carries them and the broker validates them and the SREGym adapter copies them into the strict receipt (`detector_firing_available`, `detector_timeline`, the booleans), exports the stream into the stage results as `detector_firings.jsonl` and `sdo_runtime/telemetry/`, and `stream_curve` reports them per incident. They distinguish a learned incident detector that fired before dispatch (memory used) from one that never fired (memory unused).

### Incident lifecycle event stream

The firing stream records whether and when detectors fired; the incident lifecycle event stream records the controller's own lifecycle transitions, so an operator can reconstruct a single incident's full timeline offline. It is a second durable, append-only JSONL stream (`lifecycle-events.jsonl`, `--lifecycle-telemetry-path`, default on in job mode) in the same runtime telemetry area (`/workspace/.sdo-runtime/telemetry/`), sharing the firing stream's durability mechanism: a bounded 4 MiB file rotated once to `.1`, a torn last line repaired on open, a stream from an earlier lifecycle archived as `.prev` when no state is restored, and content-addressed event ids that make a crash-replay between emitting and persisting idempotent. `incident_opened` is the exception to emit-then-persist: its incident id derives from the clock, so a replay would not reuse it. The controller queues the event and records it only after the state save that contains the incident, and re-records it on restore (the sink drops the duplicate). Each line carries the same envelope as a firing record (`schema_version` `sdo.lifecycle-event/v1`, `event_id`, `event`, `recorded_at`, `application`, `namespace`, `incident_id`) plus phase-specific fields. The `event` phases fill the transitions that previously emitted nothing: `incident_opened` (with `finding_keys`), `workspace_prepared` (`worktree`, `base_commit`), `responder_dispatched`, `responder_completed`, `incident_closed` (`health_cleared_at`), `closure_committed` (`proposal_commit`, `outcome_commit`, `reflection_commit`, which join the logical outcome by incident ID or outcome commit; the active Go memory edge stores per-incident `.sdo/outcomes/*.json`), and `incident_acknowledged`. Each `(incident_id, phase)` pair is emitted at most once, so its id is `sha256(incident_id, phase)`. `sdo/operator/runtime` stays transport-neutral: every field is a controller-internal fact (incident ids, git commit shas, worktree paths, finding keys), carrying no benchmark labels or verdicts, and the stream is derived only from the controller's deterministic lifecycle state. `ReconstructIncidentTimeline` joins the lifecycle and firing streams by incident id into one deterministically ordered timeline for offline analysis, and the record-and-replay harness pins that reconstruction against frozen artifacts.

The controller evaluates the detectors of one batch (scheduled, gate re-evaluation, closure and recovery reads) concurrently, at most eight at a time, each under its own deadline: its interval, at least 10 s, and never past the memory host's transport budget. Results are applied in batch (detector ID) order after all finish, so decisions do not depend on which detector answered first, and a hung detector costs its batch one deadline and only that detector an error. The harness plays this as seed 65 and the open-event ordering as seed 66.

#### Late findings (pull-before-act)

The incident request is immutable once the responder launches, so a detector that activates later cannot join the original batch. With `--late-findings pull`, the Go controller maintains a bounded per-incident report in a controller-owned ConfigMap. The controller projects that report into the session's read-only `late-findings` directory (the same mount for warm and cold workers) and the incident worker receives only that projection, without controller API credentials, and invokes `sdo-operator late-findings --incident-id ID`. The command returns logical detector and playbook IDs and writes a bounded pull receipt. The broker checks the worker's typed pull claim against controller-owned telemetry before recording it in closure evidence.

Detectors and Diagnose use `program.ReadView`; detectors obtain it with `program.ReadFrom(context)`. Detectors have independent detection entry points; playbook Diagnose runs only while handling their findings. Required roles bind once from that finding, and Diagnose reads additional objects by name or relation. This surface includes namespace/scoped objects, optional workload objects, frozen metrics and alerts, traffic windows, logs, TCP/HTTP probes, and accepted-source/baseline diffs. `QueryMetrics(metrics.Query)` also supports on-demand instant/range PromQL reads when a metrics URL is configured. Existing metric declarations and ID accessors remain supported. Only the runtime performs I/O. Its `ReadSnapshotProvider` creates a fresh `CycleReadView` per snapshot, deduplicates identical primitive reads (including failures), and records each logical use. Logs keep the 64 KiB / 5 s cap and probes the 5 s cap. Independent failure guards make ignored primitive/metrics errors Unknown for Diagnose and errors for detectors, so unreadable inputs cannot clear a finding; a successful negative probe remains an observation.

Captured snapshots add optional `metrics`, `alerts`, `traffic`, `reachability`, and `readings` fields; legacy object-only snapshots remain loadable. Snapshot readings hold only actual reads from that snapshot, including errors. Later Diagnose reads stay in the existing phase-specific primitive recording files. sdktest and runtime/replay load both, retaining phase isolation; absent evidence is unavailable, never healthy. Detector replay uses the recorded source/baseline diff, while closed-loop program replay retains its independent accepted-source comparison and never borrows fixed probes/logs/metrics to prove a post-plan effect. No artifact owner or production/benchmark boundary changes.

Desired state is the accepted commit's tree rendered by the deployment source's renderer (`DeploymentSource{renderer_id, config}`) through the renderer catalog. Reads use `rendered.Desired`, the one desired-state function the deployer is moving onto, with Secret values omitted; unqualified reads leave out foreign-namespace objects. A `kustomize` source renders local Kustomize units from tracked inputs, including file-generated ConfigMaps and rewritten consumer references, with krusty on a private in-memory filesystem and no executable, remote, or Helm plugins; a `raw` source rejects a selection containing a kustomization. Until path lists are retired, a legacy path list naming exactly one kustomize root reads through `kustomize`. The offline `sdo-operator render-source` JSON transport takes a ProtoJSON `deployment_source` and exposes the same non-secret inventory to benchmark restores, so generator decisions remain owned by production Go. Secret generator inputs are never loaded: stable-name Secrets remain identity references, and hash-dependent Secret names fail closed. Raw Secret manifests are also projected to identity references before recording. Benchmark lifecycle-created objects need an explicit declaration in accepted application source; production does not infer generators from benchmark code.

Typed structured plans preserve rollback preimages and patches alongside object effects; the protobuf receipt carries action/effect evidence. `CreateFromSource` restores a missing named object from the incident-bound accepted manifest, while `DeleteObject` may remove a named object in the incident namespace even if it remains in accepted source. No separate source policy, content predicate, credential-delta rule, lifecycle kind allowlist, or policy digest is required. UID and conditional-write checks, direct observation, exclusive lifecycle ownership within one batch, independent verification and rollback remain. Delete effects stay explicitly irreversible and are never auto-recreated. Restoring a referenced config object can recycle blocked managed Pods once; stale Service consumers are recycled only after a selector-related backend is Ready. Both use the existing rollout budget and UID/version preconditions, with irreversible Pod deletion effects retained in the repair receipt. Source reconciliation restores every source-declared configuration field, including RBAC fields, and preserves undeclared server defaults and controller metadata. The accepted application render lock qualifies named cluster source independently of namespace identity. See [automatic repair checks](plan-safety-authority.md).

Incident responders never merge directly into the operational branch. The broker creates isolated worktrees, checks path ownership and append-only rules, runs repository and detector validation, and accepts only attributable commits. Two repair-evidence policies are supported. `commit` retains a proposal commit for every response, including an empty attribution commit; a source repair (a responder patch) is a source commit plus a redeploy, so an accepted change to deployment inputs is deployed and verified by the trusted Deployer at closure (`lifecycle.RepairDeployer`, below) before the broker accepts it, and a repair the cluster or detectors refuse is not accepted (`source_repair_held`; fatal under `commit`, absent from the outcome under `recorded-actions`). `recorded-actions` permits a live-only repair without a proposal commit when the responder returns a structured, successful action receipt; any repository changes are still validated and committed. In both modes the controller commits the authoritative outcome and reflection, and independently owned health detectors must verify recovery. The source-deployment worker separately proposes attributable deployment commits during the initial lifecycle. Health detectors remain designer-owned. Responders can edit playbook/helper drafts during response; only validated reflection publishes those drafts and incident detectors after closure.

## Cluster permissions

SDO does not limit its identities through Kubernetes RBAC. The installer creates
one ClusterRole, `sdo-admin-<control-namespace>`, with `*` on `*` for `*`, and
one ClusterRoleBinding to every ServiceAccount SDO runs as: `sdo-controller`,
`sdo-operate`, `sdo-responder`, `sdo-image-builder` (control namespace) and
`sdo-script` (application namespace). In a separate control namespace it also
binds the user the controller impersonates for the checked removal callback.
There are no per-kind Roles, no readable-versus-writable table and no
vocabulary-versus-Role ratchet, so a repair or a replayed program is never
refused for a missing grant (a Deployment, an Ingress, a webhook configuration
or a Namespace label are all reachable). What a program or responder may change
is decided by the typed plan checks, review and runtime policy, not by RBAC.

A fresh `host`/`operate` install, `install-existing` and `inspect-existing` all
re-apply the ClusterRole and binding, so a narrowed or deleted grant is restored
on the next install or inspection. The grant is cluster-wide, so recreating the
application namespace between stages does not remove it. `--permissive-responder`
and `--responder-namespace` keep their meaning for the runtime (which namespaces
the responder may repair in, and creating the fault-backend namespaces) but add
no separate grant. The read-only detector runner Pod keeps its own narrow Role.
Credential hygiene is separate from RBAC: Secret contents never reach logs,
prompts or memory.

## Controller/responder interaction

The controller batches persistent findings into an incident request. The request includes the health objective path, architecture path, findings, surfaced playbooks, detector history, an isolated repository worktree, and the selected repair-evidence policy. A responder returns a structured result with diagnosis, applied playbooks, repository changes, and per-action receipts recording the target, timing, success, and reversibility of live mutations. Independent health detectors must clear after the response before closure. Drift opens incidents but never decides verification or closure. The controller still compares admitted owned fields and the accepted-source inventory with the live namespace, and reports what differs: `verify` and `status` carry it in `drift[]`, the continuation prompt in `source_differences`, and the closure outcome in `source_check_notes`. If health is clear the incident closes as success; if health does not clear by the configured verification timeout it closes as `failed`, whatever the drift state. Only pending deployment rollouts still hold a closure, because health samples are not settled while they run. The drift findings and events stay in the outcome. Late drift still attaches to the running responder through `attachDrift`, its moving incident view and the late-findings report. Terminal responder failures retain their existing failed closure path without treating unresolved drift as verified recovery.

Before creating a responder Job, the controller freezes its exact canonical ProtoJSON task, including the logical memory snapshot and initial program runs, in the pending runtime state. A task over 16 KiB is written first to `.sdo-runtime/requests/<job>/prepared-task.json` on the repository volume and the state ConfigMap holds only its `staged-task:sha256:<digest>` reference; a restart resolves the reference in memory and rejects missing or altered bytes. Verbose incident records above 32 KiB are frozen as content-addressed canonical ProtoJSON in `.sdo-runtime/controller-evidence/` on the repository volume before the state CAS. The state ConfigMap holds a SHA-256 annotation and omits program histories, tool calls and task bytes from both the incident and pending closure; loading verifies the digest and restores the full records before closure or outcome derivation. The digest participates in no-op and ambiguous-write identity checks. Archives survive proposal cleanup and remain available for offline evidence analysis. Every controller-written ConfigMap document (state, failed-closure archive) is held to a 768 KiB budget and fails with a typed error naming its largest fields instead of an API 422. A closure never carries the frozen task, and a reflection request carries each incident's program runs, tool calls and plan applications once, in the outcome, and none for the latest two prior outcomes. A retry reuses those bytes for the request ConfigMap and result validation. For state written before this field existed, the controller validates and adopts the already created request ConfigMap. Settle observations remain in the live incident view and `sdo status`; they do not replace the worker's dispatched task. Every worker task travels in one request ConfigMap and is held to 512 KiB (the API server rejects ConfigMaps near 1 MiB); there is no second transport. Before a responder or reflection task is frozen, Go degrades an over-limit request in a fixed order and records each step in the request's `compaction`: prior-incident history, then memory the incident does not mention, then memory documents, then raw program runs and tool calls (the outcome keeps the full record). A reflection request that still does not fit is skipped with the typed, non-retryable reason `request_too_large` in the broker ledger, and the incident closes on health alone; a responder request that still does not fit fails before any Job with a typed error naming its largest components. A task frozen by an earlier build that is over the limit is discarded and rebuilt. Every agent worker kind gets its memory request and limit from one constant pair (`WorkerMemoryRequest`, `WorkerMemoryLimit` in `worker_registry`). A worker container killed for memory ends its reflection with the typed reason `worker_oom_killed`, or `worker_resources_rewritten` when its pod was admitted with another limit than the Job asked for (a cluster admission webhook rewrote it, so resizing does not help); both are recorded in the broker ledger like `request_too_large`, and the incident closes on health. The failure text names the requested and admitted limits. Workers write one curated line (error class and short message) to `/dev/termination-log` on a startup or run failure and the controller reads only that, never logs. A permanently failed closure stays with its own incident: the benchmark adapter records it as that incident's rejected receipt and the next fault proceeds.

The controller keeps a baseline of the application namespace's configuration, taken from namespace-scoped informers over Services, workloads, NetworkPolicies, ConfigMaps, Secrets, Roles and RoleBindings. The first healthy evaluation sets it. A later healthy snapshot replaces it only after a two-minute settle period with no unhealthy evaluation, and a maintenance pause resets it. When an incident opens, the request carries `state_changes`: the objects added, removed or modified since that baseline, with field-level before and after values. ConfigMap data appears only as digests. Secrets use strict metadata-only (`PartialObjectMetadata`) list/watch requests with no full-object fallback: the baseline stores name, UID and resourceVersion, and content changes appear as resourceVersion changes. Secret type and key names are unavailable from that API, so they are omitted. Secret annotations and unrelated labels are discarded before caching. Unsupported or forbidden metadata reads leave Secrets unobserved. The controller retains only Secret list/watch RBAC, because metadata negotiation uses those same verbs; Kubernetes RBAC cannot restrict a grant to metadata representations. Kinds the controller cannot list are reported as unobserved. Objects that existed unchanged while the application was healthy never appear. The diff is computed in memory from the informer cache, so it adds no API calls on the dispatch path.

Responders run `sdo verify` through the incident tools. The controller calls the
active host's bounded Traffic RPC and independently checks current health. Agents
have no prober URL and no direct host connection. Optional workload/scenario
selection stays incident-scoped. Exit codes are 0 healthy, 1 unhealthy and 3
unavailable. The controller publishes its incident view for durable evidence;
closure retains the detection designer's independent persistence policy. Each confirmed root cause cites structured live `evidence` (a detector finding, synthetic traffic, a state change or a live observation) and the `explained_detectors` it accounts for. Scripts and manifests go in `static_context`, which is never evidence. After closure, `verify_diagnosis` checks the citations against the request and the post-response detector states. It records a verdict per cause (`confirmed`, `contradicted`, `unverified`, `unattributed` or `no-evidence`) in the outcome record. A cause is `confirmed` only when the responder's own repair backs it: each repair action receipt names the objects it mutated (`resources`), and a successful action that started before the closure's `health_cleared_at` (when the gate detectors began their final clear streak) must have touched the cause's resources. Touching an object in the dispatch-time state diff is enough; otherwise the cause is also refused when a dispatch-diff change was reverted by something other than the responder's repairs. The closure also lists `observed_state_changes`, every object the controller saw differ from the baseline while the incident was open with its first observation, so a `state-change` citation outside the dispatch diff counts only if the controller saw it before the responder's own repair of that object started: a wrong fix cannot cite its own edit (a restart's `restartedAt` stays in the closing view), and a late fault the responder reverted exactly still verifies. When health clears in time but no cause is backed, the cause is `unattributed` and the outcome is `external_recovery`: someone else restored health. A verified-clear closure where the responder made no successful change is `cleared_without_action`. Neither is a mitigation, and the SREGym strict receipt for each is valid and carries `resolution` (`external_recovery` or `cleared_without_sdo_action`) instead of requiring reflection. The verdict does not gate closure. Reflection learns playbooks and incident detectors only from confirmed causes, the broker never reflects on a `partial` or `external_recovery` outcome, and the controller does not surface contradicted or unattributed causes as prior-outcome evidence. Responders label any helper pods or Jobs they create `sdo.dev/responder-helper=true`. When the responder completes, the controller deletes them before evaluating the closure gate and records them in the closure as `cleaned_helpers`. If health clears only after the verification window, the closure carries `detector_review_required_at`; the broker does not credit that recovery to the responder, so the outcome is `partial` and reflection does not learn from it. A one-shot or bounded run exits when detector review is required; a persistent controller logs the review once and keeps observing, because its Job would otherwise restart it into a crash loop that ends detection. A split-namespace install grants this through a narrow pods/jobs delete Role.

Before dispatch, the controller deterministically selects up to three successful prior outcomes using exact finding fingerprints and, secondarily, detector/rule/resource-kind compatibility. Only compact root-cause, repair, playbook, and source-compatibility evidence enters the incident request. The responder treats that evidence as a hypothesis and must confirm, adapt, or reject it against live state; historical actions are never replayed automatically.

After independent health verification, the controller records a versioned per-incident outcome. Reflection receives the closure, current and prior outcomes, and an accepted-commit-bound logical memory snapshot. It starts in a fresh session by default or resumes the responder session when configured with a valid session ID. The versioned `outcome-reflection-direct-v1` capability edits `.sdo/` directly and runs `sdo-operator memory check`, fixing named diagnostics in the same checkout until green within its turn budget. Its result contains `updated` and affected logical playbook IDs, or `no_change`/`sdk_gap` with concrete reasons and no diff. Deprecated artifact payloads are rejected. Dispatch pins `SDO_ACTOR=responder`, `SDO_PHASE=reflection`, and `SDO_BASE_COMMIT`; the worker image contains the CLI, Go toolchain and operator sources. Go checks decision/diff consistency, then the broker requires its own exact-input `validate.Check` result against the candidate tree before publishing and triggering a controller rollout. A changed base, tree, decision, policy, captures or toolchain forces fresh validation. The durable broker ledger keeps `reflection_rejections` (attempt, typed `MemoryDiagnostic` findings, and rejection timestamp) before releasing rejected files, and marks `reflection_rejected` after the retry bound; content failures permit two corrections (three dispatches total), while infrastructure errors do not consume that learning budget. The warm rule uses confirmed prior outcomes and logical playbook IDs; a verified repeated match may skip an unnecessary reflection turn when the broker can prove no new learning is required.

Only the controller image contains the Go compiler and trusted build-cache seed for SDK and runtime dependencies. `operator/toolchain` still provisions read-only compiler mounts for worker Jobs. Broker acceptance launches the same controller executable as a child in a fresh temporary workspace, with a ten-minute wall-clock deadline and a 3 GiB aggregate resident-memory limit across its process group (sampled every 10 ms on Linux). Exceeding either bound kills the entire group and returns an infrastructure failure (exit 2), without consuming a content-correction retry. Static import and purity guards remain part of every shared check. No validator image, validation Job, isolation canary, or hand-pinned SDK schema identity remains.
The controller keeps one one-shot standby responder per application after acquiring leadership, as an optional early claimant for a task the cold path would otherwise run in a new Job. The task record, location and contract are the cold path's; there is no warm-specific task. The production Go daemon starts the registered command unchanged; the Python entrypoint imports its worker and blocks on private inherited pipes without reading incident data. A fresh daemon readiness heartbeat permits an immediate claim through the existing narrow PVC filesystem transport: a create-only claim file in the pod's inbox, so exactly one claimant wins. The controller copies the canonical checkout and session into the pod's pre-mounted directories and swaps each pair with one atomic `renameat2(RENAME_EXCHANGE)`, so the pod holds the canonical paths; every intermediate state leaves a valid canonical directory and nothing needs rollback. It then publishes the existing typed AgentTask in the read-only inbox, and the daemon binds the accepted commit and the loopback API-history proxy before releasing the Python worker. A consumed slot is never reused; replacement begins at the claim. Absent readiness, active capture storage, a dead pod or any claim failure takes the cold Job path. A published claim always rejoins its original Job, preventing duplicate incident execution after an uncertain response. On controller start every standby whose task was never published is deleted and a fresh one created; a published one is an ordinary running responder. An idle pod has no Job deadline: its heartbeat expires after 30 seconds without a controller, and a claim never published expires after five minutes. Once claimed, the normal responder budget applies. Provider session homes retain their canonical incident paths for reflection. Service accounts, credentials, security contexts and read-only corpus/history/tool boundaries are shared with cold Jobs; no new inbound claim listener or API permission is introduced.


## Controller-installation boundary

The Go `sdo/operator/install/` package installs the controller from the broker-accepted commit. The installer owns controller resources and repository synchronization. The SREGym adapter adds benchmark submission resources, readiness, `production-receipt/v2` evidence, and cleanup without changing controller semantics. Benchmark `recorded-actions` policy admits live-only repairs backed by structured action receipts; broker outcome and reflection acceptance still require independent verification.

By default the controller shares the application namespace. `install.Config.ControlNamespace` (and `sdo-operator host --control-namespace`) instead places the controller Job, repository PVC, credentials, state ConfigMap, Lease, maintenance ConfigMap, and responder and validation subprocesses in a separate per-application namespace labelled `sdo.dev/controller-namespace=true`. The application namespace then receives only two namespace-scoped grants bound to that namespace's ServiceAccounts: a read-only observer Role for the controller and the responder's repair Role; no ClusterRole is created unless named webhook observation is explicitly provisioned in the installer ceiling, and the optional Prometheus stack additionally receives a read-only discovery/node-proxy ClusterRole. The repair Role is generic namespace-scoped edit on application resources (the shape of Kubernetes' `edit` role, without Secrets or RBAC objects, and with pods/exec, attach and port-forward for parity with the Codex baseline), not a list of particular repairs. Responder pods point kubectl at the incident's application namespace. The controller installer does not rewrite application charts or manifests. A long-running install launches one stable controller. Accepted memory source changes build and hot-swap an immutable memory host before acknowledgment; the controller is never rebuilt or relaunched for memory changes. The operator-owned `sdo-controller-maintenance` ConfigMap (`state: paused|active`, `generation`) pauses detector evaluation and application observation for planned redeploys while in-flight closure, reflection, and acknowledgement continue; resuming re-lists the application namespace with a fresh informer generation, logs `controller_maintenance` with the generation, and evaluates every detector once. With `reuse_existing`, re-running the installer keeps a running controller whose install fingerprint matches and only re-applies the namespace-scoped grants.

SREGym deletes and recreates the application namespace for every problem (and reconciles away unexpected namespaces and PersistentVolumes). The benchmark's opt-in persistent mode (`persistent_controller = true` under `agent_config.sdo_codex`) therefore installs one controller per application in `<application-namespace>-sdo`, asks the harness through `SREGYM_PRESERVE_NAMESPACE_LABEL` to keep that namespace and its volume, pauses the controller after each incident is verified, and on the next problem calls the Go installer's `inspect-existing` to restore application-namespace grants before resuming with a new generation. Matching the saved fingerprint and Pod UID does not bypass this access restoration. Fault injection requires the first all-clear evaluation after that resume; its five-minute readiness deadline reports the namespace, generation, and any forbidden informer observation, with progress logged every 30 seconds. Per-problem resolution ends at controller-verified health; reflection continues asynchronously. Before the next injection the adapter waits for the previous incident's acknowledgment (`reflection_drain`), syncs the controller's repository into the new workspace, and writes the previous problem's strict receipt; pipeline teardown drains the last incident, then delegates runtime shutdown to `sdo-operator stop`, retaining the repository PVC and accepted state.

`sdo-operator stop [--control-namespace <namespace>] [--kubeconfig <path>]` owns production shutdown. With no namespace it inventories all namespaces; with a namespace it touches only that scope. It stops controller/operate dispatchers before worker Jobs, Pods (including their proxy sidecars), worker helper resources. Inventory recognizes existing installer names and runtime labels, including worker Job template labels, so it works after the controller disappears. It waits for deletion up to `--timeout` and returns JSON `removed` and `leftovers` lists; errors exit nonzero. `--inspect` returns the same inventory without deleting. Namespace, RBAC, PVC, ConfigMap, Secret and Git contents are preserved. This command has no benchmark dependency.

The benchmark adapter's `persistent abort --state <path>` kills only registered same-user process identities, stops each recorded controller with its own kubeconfig without draining, removes benchmark bridge/registry workloads and the application namespace, and verifies runtime and helper absence. Cleanup targets are saved before lifecycle installation, retained for retries, and pending incidents become timestamped `aborted_incidents` in benchmark state. The launcher in `scripts/run_sregym.sh` traps SIGINT/SIGTERM and invokes abort. Its private process-group guardian kills host helpers and the runner when the launcher vanishes, including SIGKILL. Helper commands are supplied as foreground argv through `--helpers` or `SDO_RUN_HELPERS_FILE`; the registry stores PID, boot ID, start time, UID and group, never arguments or credentials. A stable abort locator points to the state in the result directory, preserving deferred receipt publication. The runner imports only the adapter's process-registry binding utility. Historical unregistered helper processes cannot be discovered or stopped by this registry.

The adapter reads controller settings from `[agent.sdo_codex]` in an experiment or `[defaults.agent_config.sdo_codex]` in a pipeline, exported by the runner as `SREGYM_EXPERIMENT_AGENT_CONFIG`. `deployment_source` is a table naming the renderer: `renderer = "raw"` with `paths` (non-empty repository-relative manifest files or directories) or `renderer = "kustomize"` with `path`; the hotel source adapter's `kubernetes/` is a kustomize root, so use `renderer = "kustomize", path = "kubernetes"` for that application. The adapter passes it to `sdo-operator install-existing --deployment-source <ProtoJSON>` (`benchmarks/sregym/adapter/deployment_source.py`), which records it as `.sdo/deployment/plan.yaml` in a human commit before the install; the controller takes no source flag and reads the plan from the accepted tree, and no path list reaches it. `deployed_manifest_paths` and `--deployed-manifest-path` are rejected. A seeded lifecycle needs a source: either this table names one or the seeded repository already carries `.sdo/deployment/plan.yaml`; `install-existing` fails before any cluster call otherwise, and a controller started on a tree without a plan refuses to start. The driver does not infer a source from seed provenance. Repeated `--deployment-source-paths` CLI arguments replace the configured source with a raw one. Persistent SREGym lanes installed with the old settings hold old broker evidence (including evidence that still carries its plan) and controller config (the removed source and path flags) and must be reinstalled. Set these before installing the controller; changing settings on an already running persistent controller requires a new installation.

Persistent benchmark experiments may additionally preserve shared cluster infrastructure behind an explicit SREGym-only flag. A durable in-cluster marker gates reuse, and the warm storage/observability installation becomes the reconciliation baseline; application and injected-fault state are still cleaned between attempts.

The installation code provides manifests and orchestration logic; the always-running runtime is `sdo/operator/runtime/` in Go. Unit and Go integration tests validate contracts; successful operation on a particular cluster still depends on cluster access, images, credentials, storage, and the target application's deployment artifacts.

## Responder Kubernetes API history

Native responder Jobs start one Go recording proxy as a Kubernetes native sidecar
(requires native-sidecar support, Kubernetes 1.29+). It listens on plain HTTP at
`127.0.0.1:18080`; the generated application kubeconfig points there without
client credentials. The proxy uses the same Pod service account upstream, with
its normal TLS CA and rotating token, so existing responder RBAC still applies.
The native controller selects the existing validator image for the proxy binary,
independent of the registered agent's language or image. Startup probing gates
agent launch. No controller Service, TokenReview, serving certificate, or identity
mapping is needed: the controller passes the incident ID when launching the Job.

The memory edge prepares `.sdo-runtime/sessions/<digest>/api-history/` on the
repository PVC. Only the sidecar mounts that directory writable; responder and
fresh/resumed reflection mount it read-only. The sidecar gets no model-provider
credential mounts or environment. It appends request start/end envelopes with
UTC times, verb, GVR, namespace, name, subresource, status and opaque
resourceVersion. Sanitized response bodies are SHA-256-addressed and deduplicated.
The proxy uses its own strict projection, independent of controller snapshots.
Its positive per-kind allowlist retains Service routing ports and type; workload
replicas, rollout type, container images/ports/probe shapes/resource budgets and
reference names; Pod readiness, restart/state reasons and exit codes; endpoint
address counts and ports; Event reason/type/object/count/timestamps; and reviewed
HPA, PDB and NetworkPolicy spec structure. Labels and selector match labels retain
keys with empty values; selector expressions retain keys/operators, never values.
Service clusterIP and Pod podIP become presence booleans; endpoint addresses become
ready/not-ready counts. Secret/ConfigMap payloads remain key names only. All annotation contents, environment values, commands/arguments (including probe exec), probe
headers/hosts and all HTTP probe paths (including pathname segments, queries and
fragments), mount paths and messages stay opaque under an explicit `redacted`
marker. Probe handler kind, port, scheme and timing remain visible. Image strings
are parsed and normalized as named container references; invalid references, URL
schemes, userinfo, queries and fragments are omitted, while valid repository, tag
and digest identifiers remain visible. Conditions, current/previous container
states and Events retain only the finite reason vocabulary in
[projection_leaves.go](../sdo/operator/apihistory/projection_leaves.go); other string
reasons become `redacted`. Closed enums, quantities, CIDRs, named ports, timestamps
and downward-API expressions are validated, with canonical quantities, CIDRs and
UTC timestamps. Bulk env references expose name/optional, never a key selector.
Identity names, label/selector keys, reference names/keys and valid image
identifiers are an accepted disclosure boundary: user-chosen identifiers can
encode secrets, so this is not a universal credential-absence guarantee. These
rules apply to new recordings; existing blobs retain their original projection.
The identity policy is centralized in
[identifiers.go](../sdo/operator/apihistory/identifiers.go), with these per-field grammars:

| Retained field | Disclosure grammar |
| --- | --- |
| Object names (except Service), node names and reference names | DNS-1123 subdomain, at most 253 characters |
| Service object names | DNS-1035 label, at most 63 characters |
| Namespaces, container/status/HPA-container names, volumes and mount names | DNS-1123 label, at most 63 characters |
| Label keys, selector keys and referenced downward-API annotation/label keys | Kubernetes qualified name: optional DNS subdomain prefix and a 63-character name |
| Secret/ConfigMap data keys and env key-selector keys | Kubernetes ConfigMap key: alphanumeric, `.`, `_`, `-`, at most 253 characters; reserved dot paths excluded |
| Environment variable names and reference kinds | C identifier (`[A-Za-z_][A-Za-z0-9_]*`), a conservative disclosure policy |
| Container port names, string targetPorts, network-policy and probe ports | Kubernetes named port: lowercase alphanumeric/hyphens, at most 15 characters, with a letter |
| Service and endpoint port names | DNS-1123 label, at most 63 characters |
| Reference apiVersion | DNS-1035 version label, optionally preceded by a DNS-1123 group subdomain and `/` |
| HPA Pods/Object/External metric names and Resource/ContainerResource resource names | Kubernetes qualified name; custom names are retained only in that grammar, even if API admission allows broader text |
| Pod condition types, including custom readiness conditions | Kubernetes qualified name |
| Workload condition types | Finite reviewed vocabulary: `Available`, `Progressing`, `ReplicaFailure`; all other strings become `redacted` |
| Request group; version; resource/subresource; namespace; name | DNS-1123 subdomain; DNS-1035 label; DNS-1123 label; DNS-1123 label; DNS-1123 subdomain, respectively |
| Object/list/item and envelope resourceVersion | Nonempty ASCII decimal digits; other opaque values become tokens |

Invalid identity leaves and map keys are omitted without echoing input or validator
errors. HPA `scaleTargetRef` and object-metric `describedObject` use the actual
CrossVersionObjectReference shape (apiVersion/kind/name), with no namespace.
Invalid request names/subresources and nondecimal resource versions instead become
`opaque:<HMAC-SHA256>` tokens. The hash uses a random 32-byte key stored privately
in that history's `identity.key` (0600), with a field domain separator. Equality
is preserved within each field across objects, lists, envelopes and recorder
restarts in one history, without correlating separate histories. Known
subresources such as `status`, `scale`, `log`, `exec`, `attach`, `portforward`,
`token` and `finalize` pass through. Other valid subresource identifiers also pass;
invalid group/version/resource/namespace segments are omitted. Altered request
identity marks the envelope partial so an invalid namespace cannot widen an
absence claim. The key and raw rejected values never appear in evidence CLI
output. Numeric resource versions are retained as identities, not interpreted as
ordered counters. A valid referenced annotation key remains visible in a
validated downward-API expression; its annotation value remains opaque.

Unknown fields and wrong JSON shapes cannot widen the allowlist. The
enforced field-by-field allowlist is in [projection.go](../sdo/operator/apihistory/projection.go). Unsupported representations,
all log bodies, watches and connection payloads retain envelopes only. Body
capture requires declared `application/json` (optionally UTF-8 charset) and absent
or identity `Content-Encoding`; other declarations remain metadata-only even if
the bytes look like JSON. Forwarded status, headers and bytes are unchanged. Headers
and request bodies are never recorded; the reverse proxy discards upstream error
logger text, including body-copy errors.

The default incident budget is 64 MiB / 10,000 envelopes, with a recording queue
bounded by 1,024 entries / 8 MiB of already-projected envelopes and bodies.
After forwarding returns, up to eight transient workers project responses no
larger than 256 KiB. Larger bodies or saturated projection workers retain
metadata and a marked gap; raw bytes never enter the recording queue or storage.
A reserved manifest reports completeness, dropped counts, bytes, writer status
and restart epoch. Unfinished requests and restarted writers invalidate
continuity. Every initialization attempt first leaves a recording-disabled
marker until successful open. A directory lock exposes the live forwarding
generation to read-only readers even when recording writes fail and a previous
closed manifest survives. Disk, queue and cap failures leave forwarding active
and mark gaps; unavailable storage is Unknown. Upstream failure returns a
Kubernetes-shaped 502; write connections are fresh and never automatically
retried. Every response and stream reaches the caller unchanged. History follows
existing incident-session cleanup, with no additional retention policy, and adds
no durable `.sdo/` artifact class.

Reflection can run `sdo-operator evidence history`, `show --event N`, and
`state Kind/namespace/name --at RFC3339|before-first-mutation|after-fix` using
`SDO_API_HISTORY_DIR`. These commands read files only. State is explicitly last
observed, stale and Unknown at the requested instant because metadata-only
watches provide no continuity. Complete unfiltered scoped lists or named GET
404s can observe absence only at their observation times. Lookups match an
explicit GroupResource; `Kind.group/namespace/name` can qualify built-in kinds,
and unsupported groups stay Unknown. Cluster-wide lists retain positive matches
using item namespaces, with no inference of broader absence. The first mutation
boundary includes opaque exec/attach/port-forward regardless of query parameters
and excludes only recognized supported dry-run writes; crossing requests,
partial history and filtered/paginated lists cannot establish broader facts.
The controller writes `recovery.json` only for independently verified successful
or cleared closures; `after-fix` requires compatible observations beginning after
that marker. A final API write is never recovery evidence. Proxy history does
not replace captures, pre-apply checkpoints or action receipts, and is not a
replay source, coverage policy or `no_recorded_repair` implementation. Direct network
traffic, alternate kubeconfigs and controller SDK reads remain outside its view.

## Application-name genericity

Production SDO (`sdo/**` Go, Python and protos, `sdo/skills/**`, and agent prompt templates) must not name specific applications. The denylist is data: the directory names under `apps/` plus the SREGym application names and `gitlab` in `scripts/app_name_rules.json` (`toy`, the synthetic fixture, is exempt). `scripts/check_app_names.py` matches them case-insensitively on word boundaries, with spaces, `_` or `-` between words optional, and runs from `check_errors.sh`. Existing occurrences are a per-file ratchet in `scripts/app_name_allowlist.json` with a reason each; counts may only drop, and a stale count fails until lowered. Describe a behavior generically instead of citing the application that exposed it.

Startup inventory preparation renders accepted source directly, including while onboarding is pending. Inventory readiness, health authority or confirmed observations never consumes an attempt. ACTIVE maintenance generation updates preserve running probes, baseline and queued changes. A real pause/resume starts a new confirmation sampling deadline, retaining frozen install identities and every prior invalidation, target configuration and observed serving port; pre-resume samples cannot authorize completion. Verified memory-only publications preserve the frozen install boundary. Unconfirmed probe windows are recorded as pending and cannot establish health. When confirmation windows are ready, the controller schedules one full detector sweep on the current snapshot even if ordinary event batches are partial, preserving every ordinary scheduler deadline. The original confirmation deadline still rejects late clear samples; observed commit or inventory contradictions invalidate the pending window. Immutable control records `sdo-namespace-onboarding-window` and `sdo-namespace-onboarding-rejected` prevent restart from forgetting sampling or rejection. An interrupted sampling window fails closed without recapture; ordinary fault detection continues. Rejection or expiry does not claim an unready evaluation. A previously serving port still uses the unchanged failure confirmation gate. Target configuration changes or a subsequent successful dial invalidate an exclusion. Controller logs report install-to-record duration; three default 10-second probe rounds add at most two ordinary observation intervals plus probe and scheduler time. The remaining host health verifier checks cluster Service DNS before starting its local prober and returns `probe transport unavailable` when that transport is absent. Source manifest references declare dependency identities with typed unverified-content gaps. Later unknown objects still block closure; onboarding never grants content, repair or learning authority.

Explicit memory adoption is compile-only and does not establish health provenance. Matching inherited broker-validated judge inputs avoid refresh entirely. Otherwise startup refresh establishes authority before onboarding can claim its evaluation; a continuous single-parent chain of validated health-judge publications, with unchanged application inputs and human objective preserves the original install snapshot and commit. Source changes, objective changes, merges and unrelated publications cannot use this exception. The frozen onboarding ConfigMaps are never rewritten to a refreshed commit.

Source inventory drift compares top-level non-secret informer objects against a cached accepted-deployment index. Source-absent namespace objects, RBAC bound to application ServiceAccounts and deletion-pending declared objects become latent `drift.unexplained` findings, including objects present on startup unless declared as accepted-source dependencies or present in the installer’s frozen environment inventory. This inventory records only pre-existing identities; it does not authorize health or reachability exclusions, hide declared source obligations, or accept objects first observed after installation. Namespace Roles/RoleBindings and bound ClusterRoles/ClusterRoleBindings are observed without Secret access; RBAC comparison includes rules, subjects and role references. SDO runtime objects, generated descendants of source objects and endpoint/event/status churn are excluded. The rolling healthy baseline remains diagnostic and cannot absorb these source contradictions. Both self-check and closure use the same in-memory inventory check with no added API or model call. Inventory renders accepted source directly. A restart before it loads makes a verified closure wait for a bounded time and never retires it; the unloaded inventory is noted on the outcome. Dependency-content gaps remain typed diagnostics in the read-only report (`evidence_gaps`); they do not become inventory drift or block presence checks. Remaining drift is information: the responder is shown it and the outcome records it. An exact observation-bound benign assessment with a reason and valid evidence is still recorded without repair or cause credit. ControllerState fields `accepted_source_drift` and `accepted_source_drift_revision` preserve checked acceptances across restart and memory-only commits, while application-source or object configuration/incarnation changes invalidate them. The generated controller exposes `--evaluate-once --source-drift-report /absolute/full.json` for read-only inspection; supply the accepted app root, namespace and explicit deployed manifest selection. Reset still cancels and awaits controller and worker Jobs before deleting captures or checkouts.

## Memory host

Accepted memory executes only in a bounded memory-host child. The generated
controller imports runtime alone and stays long-lived across accepted revisions.
Remote SDK adapters register from Ready; accepted detector, program and traffic
constructors run only in the child. Evaluate, Diagnose and Mitigate use
the typed `MemoryHostService` over gRPC on a private Unix socket. Informer snapshot projections fan out as complete, contiguous mirror deltas to
active and prepared hosts. Each call leases its child (retirement waits for the
lease) and evaluates exactly the mirror sequence its view was published at; the host keeps
its last sixteen sequences readable. No lock or lease is held across a call into detector or
program code, so one detector's hang or failure never delays another detector, a swap, a
failure or recovery. The host ends a detector shortly before the transport deadline,
reports a detector error, and never runs the same detector twice at once. Optional input
windows remain request-local.
Unchanged projections retain their sequence. Errors and disconnects remain
detector/program errors, never clearance or an authorized empty plan.

`builder.Workspace.BuildMemoryHost` builds the host from the same staged
diagnostics, playbooks and shared library used by `validate.Check`. Validation
builds that executable too. The controller alone executes plans. The host owns
bounded namespace-scoped log reads and GET/HEAD/TCP probes and returns typed
primitive receipts; the controller records those through its existing program
evidence and corpus sinks. Source/baseline diffs arrive as frozen typed read inputs. Source comparison uses
the accepted manifest projection without issuing a Kubernetes dry-run PATCH;
unavailable inputs fail closed.
No mutation client or controller callback is exposed to programs.

| Component | Responsibility |
| --- | --- |
| `memoryhost/` | Protocol server, registrations, deterministic snapshot execution, receipts, mirror fan-out and manager leases |
| `memoryhost/hostio/` | Declared nondeterminism edge: child launch/reaping, memory bound, Unix transport and read-only live reads (`KubernetesRead`, `DatabaseUsers`, `Observe`, `PodUsage`/`NodeUsage`, `WebhookCAMatchesSecret`, `AdmissionWebhooksFor`, logs, probes) confined to the observed namespace, refusing the control namespace |
| `kubereads/` | Shared read-only Kubernetes reads (transports injected by the controller or the host edge) |
| `runtime/memory_host.go` | Remote SDK detector/program adapters, input transport and evidence forwarding |
| `builder/memory_host.go` | Staged host build; digest binds the launched executable |

The artifact ownership matrix is unchanged: the host reads accepted diagnostics
and playbooks and authors no durable artifact; the controller and broker retain
outcome and publication authority. These packages are production scope and have
no benchmark imports.

Accepted closure commits compile a candidate in an isolated builder workspace while
existing detection continues. The controller loop catches the candidate up from
its latest informer projection, verifies revision, executable digest and complete
mirror sequence through Manager, then activates it and reconfigures future detector
schedules, persistence policies, input observers and program/drift catalogs.
Open incidents, finding counters and retained bindings survive. Old RPC leases
finish before retirement. A crash fails closed and demand restarts/replays the same
immutable artifact; a newer activation fences late recovery.

The controller launches once and remains long-lived;
closure acknowledgment waits for the active host's matching revision/digest and
durable activation receipt. The temporary legacy ledger wire fields named
`rollout_expectation` and `rollout_receipts` carry that provenance, with the
`memory_host_activation` phase replacing `controller_restart_relaunch`.
Source-deployment provenance remains separate. `memory_host_activation` controller
log records include the accepted commit, binary digest, activation latency in
milliseconds and unchanged controller build revision.

The same child also constructs accepted traffic generators and
owns their engines, workload scheduler, windows, verification bursts, primitive
probes and reachability dial rounds. Typed Traffic RPC operations start, stop,
reset and read this state. Prepared hosts remain idle; activation and crash
recovery restore the requested scheduler state. Maintenance stop joins all
workloads. Each revision starts with fresh observations.

The temporary memory-host flag, controller rebuild/relaunch supervisor, prober
pod and publication/install wiring are deleted. Bounded health evaluation starts
the same validated host artifact. Responder `sdo verify` travels through the
incident tool transport to the controller, which calls the active host over RPC;
agents never connect to the host or an independent prober. The host cannot mutate.
Startup and resume do not turn controller build provenance into host activation:
only verified active host identity can satisfy the broker activation receipt.

The memory component owns a private `memory/internal/memoryio` edge for Git
reads, isolated-index whitespace checks, shell syntax and toolchain lookup.
It exposes bytes and errors, never process handles. The artifact ownership
matrix and repository scope matrix above remain unchanged: this production
adapter belongs to memory and has no benchmark dependencies.

Deployment orchestration injects command execution, polling waits and Job-name
suffixes. Its private `deployment/internal/deploymentio` adapter owns the
production process/socket/timer implementations. It stays within the deployment
component and production scope above; artifact ownership remains unchanged.

Offline compiler-test cache preparation delegates bounded module downloads to
`operator/toolchain`, which returns diagnostics without exposing a process
handle. CLI memory defaults read the environment through the existing CLI
process adapter; explicit environment injection remains supported. Runtime
time-scale parsing consumes a string from its lifecycle edge.

Runtime accepted-manifest reads, program dependency revisions and learning
corpus reads keep their policy in runtime while repository subprocesses live
in `runtime/internal/lifecycleio`. The edge returns bytes/errors and interprets
Git diff status 1 as a confirmed difference; process handles remain private.

Program trust fingerprints executable sources and imported helpers, excluding Markdown and Go test files. Successful plan credit remains bound to the applied resources and requires an independently successful incident outcome; a global health failure with no explicit unrelated finding remains a failure. More than one binding of a program can earn equivalence evidence, but an incident contributes at most one trust success per program.

API history completeness is bound to a controller-written attempt generation
outside the recorder directory (`api-history.generation`). The memory edge
rotates it before launching an incident Job; launch fails if that write fails.
Sidecars rotate it again before opening the recorder. Agents mount both history
and generation read-only, and offline readers reject a stale or missing token
even after a failed recorder exits. This runtime boundary remains outside `.sdo/`.

Reflection work is grouped only by confirmed_root_causes resource sets. Go settles exact covered bindings and records observed fixed-capture false matches as required NoMatch cases. Unwritten bindings, unproven final plan equivalence and unbound writes remain typed questions in the resumed incident session; observations outside confirmed groups stay explicitly unassigned. No inferred cause, merge/split decision or trust credit is created for a question. Affirmative PlanApplication.final_equivalence_verified and an explicit fixed NoMatch are required for covered eligibility. Missing final proof or an absent fixed verdict remains a question. OutcomeRecord.reflection_eligibility version 1 records program revision, bindings and disposition before the outcome commit; trust and corpus publication consume that same result. Historical outcomes without trusted eligibility add no partial success credit. Newly authored programs may earn one origin credit through executable-v1 broker validation and a controller-verified bound fixture. Final completion object reads are cached once per distinct resource across applications. The final-equivalence field distinguishes an uncredited question from a failed execution without changing the historical applied/verification evidence. The fixed-negative provenance phase is SDK-defined, can label only NoMatch cases, and selects actual fixed-phase primitive observations. All materialized files still pass the same independent validator and broker.

Go counts confirmed causes with no recorded successful repair before the outcome commit and persists the count in settled eligibility. The broker allows a `no_recorded_repair` decline only for Go-flagged causes. First-party incident records expose the count.

Controller maintenance normally resets the configuration baseline after a planned redeploy. Its explicit `preserve_baseline` observation option keeps the last healthy baseline while evaluation is paused. The benchmark injection-validity barrier uses that option so partial invalid writes cannot dispatch responders, while valid latent faults remain visible after resume. Go owns the maintenance state and baseline policy; no benchmark identities enter this interface.

Repository staleness does not exist as a closure concept: every change to the operational repository is made by SDO, so an incident's investigation, closure and acknowledgment survive any advance of the accepted head, source, objective, health policy or detector scope. The health guard only requires the running detector bundle to match the accepted health policy (otherwise the controller restarts to adopt it and resumes the same work). Closure is decided by the live recheck under the detectors in force; a replayed closure that the broker already committed returns its existing receipt. The broker replays a verified proposal onto a moved head and re-verifies that the replay carries exactly the verified source.

The complete native receipt may reach the broker ledger before the controller persists its receipt state. After health adoption, the same ownership proof may resume that frozen closure’s idempotent broker effect, returning the existing receipt without publishing again. An absent/incomplete native receipt still fails closed. The restart fixture must cover both sides of the controller receipt persistence boundary.

A complete authenticated native receipt is recovered as an existing decision. Its replay does not re-run the independent closure decision after adoption. The durable effect identity still applies; incomplete receipts use the ordinary live recheck, which runs under the detectors now in force (a changed observation scope never supersedes a closure).
Automatic plans use the controller-derived incident namespace, with no hand-maintained application policy, content predicate, credential-delta gate or accepted-value restoration requirement. Save-time compile/vet and informational test/replay, post-apply verification, rollback, broker ownership and the state budget remain. Plans do not acquire cross-namespace or cluster mutation authority. See [automatic repair checks](plan-safety-authority.md) for the exact scope, ranking, fallback, defaults and RBAC changes.

The production `run.go` `LoopFactory` enables the mitigation menu by default. `SDO_RESPONDER_MENU=0` opts out; empty or `1` enables it and other values reject launch. The dispatcher advertises `SDO_MITIGATION_SESSION=1` only for enabled menus. Durable provider checkpoints use the independent `SDO_RESPONDER_SESSION=1` flag even when the menu is disabled. Menu execution uses the ordinary executor, accepted source, health verifier and controller credentials. No policy document or menu-specific execution gate is required.

Program statistics retain independently verified success credit across broker-validated program revisions and record revision-attributed failures. The incident-open coverage view lists all matching programs in stable program/revision/binding order, each explained finding once, and every unexplained finding once. Failed verification leaves landed repairs in place for the responder to assess. Response loops default to 10, verification to 5 minutes, and validation correction retries to 5.
